# Issue #14: Optional TOTP with recovery codes — verification

Checks were run in the Sandcastle sandbox (Node 26.10.0, pnpm 12.10.0, no
Docker) against a fresh `git clone` of this branch at the last code commit
of the issue (`673cec4`), after `pnpm install --frozen-lockfile`.

## What was built

- **Storage** (migration `0005_totp`):
  - The one-row `owner` table gains `totp_secret`, `totp_pending_secret`,
    `totp_last_time_step` and `totp_enabled_at`.
  - Check constraints refuse a secret that is not sealed (`aio1:…`), and
    require a secret and `totp_enabled_at` to be set together.
  - `recovery_codes` keeps only each code's SHA-256 and when it was used.
  - `sign_in_events.second_factor` (`totp`, `recovery_code` or null) says
    which second factor a sign-in checked.
- **The secret** is generated by `otplib` (160 bits, SHA-1, 6 digits, 30 s
  steps, which every authenticator app reads). It is sealed with
  `ENCRYPTION_KEY` through the encryption of #13 (context
  `owner.totp_secret`) before it is stored. The QR code is an SVG `data:`
  URL made by `qrcode` on the server.
- **Codes:**
  - A TOTP code is accepted one step either side of the clock.
  - Each time step works once (replay protection): one atomic
    `UPDATE … WHERE totp_last_time_step < $step`.
  - Recovery codes are 16 characters of Crockford base32 (80 bits) in
    groups of four. Case, spaces and dashes are ignored. Each works once,
    through an atomic `UPDATE … WHERE used_at IS NULL`.
- **API:**
  - Admin routes, all `owner` routes (a session and the CSRF token):
    - `GET /api/totp` returns `{ enabled, recoveryCodesLeft }`.
    - `POST /api/totp/setup` returns `{ secret, otpauthUrl, qrCode }` with
      `Cache-Control: no-store`. The secret is kept as pending; TOTP is
      not on yet.
    - `POST /api/totp/enable {code}` checks the code against the pending
      secret, turns TOTP on, and returns the ten recovery codes, this once
      (`no-store`). A wrong code gets `422 wrong_code`. Only the latest
      secret set up can be confirmed.
    - `POST /api/totp/disable {code}` takes a current TOTP code or an
      unused recovery code, and deletes the secret and every recovery
      code. Wrong codes get `422` and count against the rate limit.
  - **Signing in with TOTP on:** `POST /api/login` with the right password
    answers `200 {"secondFactor":"totp"}` and sets an HttpOnly,
    `SameSite=Strict` challenge cookie (`Path=/api/login`, 5 minutes;
    only its SHA-256 is kept, in memory). No session cookie is set.
    `POST /api/login/totp {code}` finishes the sign-in with a TOTP code or
    a recovery code. It answers `401 wrong_code` for a wrong or used code,
    and `401 sign_in_expired` with no live challenge.
  - **Rate limit (#12):**
    - Wrong codes count like wrong passwords, so five lock the client out.
    - A right password that still needs its code is *withdrawn*: it does
      not count, but earlier failures stand (`LoginAttempt.withdraw()`).
    - A new password step therefore never resets the count for code
      guesses.
  - Logs say which factor was used, and how many recovery codes are left
    after one is used. They never contain the secret or a code.
- **Redaction (#13):** the `secret=` query parameter (otpauth URIs) and the
  values of `totpSecret`, `otpauthUrl` and `recoveryCode(s)` keys are now
  redacted.
- **Web:**
  - The login page asks for a code (or a recovery code) after the
    password. It goes back to the password when the sign-in expired.
  - The admin page has a "Two-step sign-in (TOTP)" card. It shows the
    status, and turns TOTP on with a QR code, the secret and a confirming
    code, then shows the ten recovery codes once ("I have saved them").
    It turns TOTP off with a current code.
  - The card recommends TOTP whenever the page's hostname is not
    `localhost`, `*.localhost`, `127.0.0.0/8` or `::1`.
- **README:** a TOTP paragraph under "Signing in".

## Acceptance criteria

### Verified in the sandbox

- [x] **`pnpm lint`, `pnpm typecheck` and `pnpm test` pass.** All three
      exit 0 from a fresh clone (output below). `pnpm build` passes too.
- [x] **Integration tests: enable, sign in with a code, sign in with a
      recovery code (which then stops working), disable.** All four run in
      `apps/server/src/auth/totp.test.ts`, which drives the whole app:
      - `turning TOTP on > shows a QR code and secret, confirms a code,
        then shows ten recovery codes once`;
      - `signing in with TOTP on > asks for a code after the password,
        then signs in with it`;
      - `signing in with TOTP on > signs in with a recovery code, which
        then stops working`;
      - `turning TOTP off > needs a current code, then signing in needs
        only the password`.

      The same file also covers replayed codes, the five-minute expiry, the
      rate limit on wrong codes, CSRF and sessions, and that nothing secret
      is logged.
      - The same four steps run against Postgres 18 in `store.test.ts >
        turns TOTP on, signs in with a code and a recovery code, and turns
        it off through the app`. That test uses Testcontainers, so it is
        skipped here; it was run against an embedded Postgres 18.3 (below).
      - They also ran against the real server with curl (below).
      - **Negative check:** with the in-memory store changed so that a
        recovery code is never marked used, `signs in with a recovery
        code, which then stops working` fails, along with one other test
        (output below). The change was then reverted.
- [x] **The TOTP secret is encrypted at rest (#13).** (From "What to
      build".)
      - In memory, `turning TOTP on` asserts the stored value is `aio1:1:…`
        and does not contain the secret.
      - In Postgres, the check constraints refuse an unsealed secret
        (`refuses a TOTP secret that is not sealed`), and the through-the-app
        test reads the row back sealed.
- [x] **The UI recommends TOTP when the page is not served from
      `localhost`.** (From "What to build".) This is tested by
      `apps/web/src/totp-settings.test.tsx`: `isLocalhost` cases, the
      recommendation off-localhost, none on localhost or once TOTP is on.
      The web flows (turning on, wrong code, turning off, the login code
      step) are component tests there and in `login-page.test.tsx`.

### Not verifiable in this sandbox

- **The Testcontainers Postgres tests as written** (3 new ones in
  `apps/server/src/auth/store.test.ts`), because there is no Docker.
  - They were run against an embedded Postgres 18.3 instead, by the method
    of #12: `@embedded-postgres/linux-x64@18.3.0-beta.16` in `/tmp/pg18`,
    port 54329.
  - Scratch copies of the test files replaced only the container fixture,
    using the harness's own `preparePostgresServer`. Nothing from this is
    committed.
- **Scanning the QR code with a real authenticator app on a phone.** The
  URI follows the `otpauth://totp/` format that `otplib` documents, and its
  codes match `otplib`'s RFC 6238 generator. Whether a given app reads the
  SVG must be checked on the host, in a browser.
- **The admin page and login page in a real browser.** Here they are jsdom
  component tests. Playwright (#17) is set up later in this batch.

### Notes

- **Disabling with a recovery code.** The issue says "Disabling requires a
  current code". A recovery code is accepted too: an Owner who has lost
  the authenticator signs in with one, and must then be able to turn TOTP
  off and set it up again. Such a code is used up like any other.
- **No regeneration of recovery codes.** The issue does not ask for it.
  Turning TOTP off and on again makes a fresh set.
- **Sign-in challenges are in memory**, like the rate limit. A restart
  means typing the password again.
