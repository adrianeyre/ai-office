# Browser pages use a Gateway Key only when its Browser access allows them, never with credentials

The Owner wants web apps of their own (a CV checker on `http://localhost:4870`, later the same app on an https GitHub Pages site, and others to come) to call the AI Gateway's `/v1/messages` straight from the browser, with a Gateway Key. Until now the Gateway answered no CORS preflight, so a browser refused every such call before it was sent, and the pen tests pinned that another site's page cannot call `/v1`. So **each of the Owner's own tools' Gateway Keys has a Browser access**, set in API Key Management: **off** (the default, for every key until the Owner sets it), **only these origins** (exact origins, `scheme://host[:port]`), or **any origin**, so the Owner can make a key once and use it from any web app without coming back to it. **Browser access is opt-in, per key, and never credentialed**: no answer carries `Access-Control-Allow-Credentials`, because the Gateway authenticates by Gateway Key alone and a cookie must stay useless to it. While no key allows a browser, the Gateway answers exactly as before.

## Considered Options

- **Keep refusing every browser**: the Owner's page would need a server of its own just to hold the key and forward calls, which is what the Gateway already is.
- **One office-wide list of origins, in AI Settings**: the first design. It opens every key to every listed page unless each kind is carved out, and the Owner must come back to the list for each new app. Rejected for a setting on each key, beside its Token Caps and AI Providers.
- **Allow origins by pattern** (`https://*.example.com`): more to get wrong, and `*.github.io` is every GitHub Pages site, not the Owner's. A key's list takes exact origins only, at most 20; a key meant for any page says so with **any**.
- **Let the app's own routes answer preflights too**: the app authenticates by session cookie, so that would be cross-site request forgery by design. Only `/v1` is affected; no `/api` route answers a preflight.
- **Per key, exact origins or any, on `/v1` only, without credentials** (chosen).

## Consequences

- A preflight presents no key, so it is answered (`204`, before the Gateway Key is asked for, before an unknown route is refused and before any body is read; not recorded) when **any** key in use allows its origin: an Owner tool's, enabled and not revoked. Which keys allow which origins is kept in memory, read again at once when a key changes and at least once a minute, so a preflight costs no database read. Otherwise it is `404` with no CORS header, as before.
- So the preflight alone is no lock: once one key allows any origin, every page's preflight is answered. **The request is the lock**: once its key is checked, a request whose `Origin` that key does not allow is refused `403` in the route's own format ("This API key doesn't allow browser requests from …"), before anything is sent to an AI Provider and without a CORS grant, so another site's page can never use a key that is off, an Agent's or the Terminal's. A request whose `Origin` names the address it was sent to (a page of AI Office's own) is not another site's; a request without `Origin` (Claude Code, curl, sandboxes, SDKs on a server) is answered as before.
- Every answer to a request whose key allows its origin (a `503` with no AI Account, a Token Cap refusal, a `404`, a streamed answer) names the origin, with `Vary: Origin`, and lets the page read `retry-after`, the request id and `x-ai-office-refusal`. Without that, the browser hides the real error behind a CORS failure. A `401` or `429` sent before a key is checked names it when any key allows the origin: no more than the preflight already said. Whatever an AI Provider said about its own CORS is not passed on.
- The preflight allows `GET` and `POST`, and only the request headers a page needs: a Gateway Key (`authorization`, `x-api-key`), `content-type`, Anthropic's and OpenAI's own headers, and the `x-stainless-*` headers their SDKs send, without which those SDKs cannot call from a browser at all. Never `user-agent`, which tells the Gateway which agent tool is calling (FR-35), so a page never passes for Claude Code and a subscription never serves a browser; and never a cookie. Which AI Account serves a call, and the rule that a subscription serves only its own agent tool, are unchanged.
- **A Gateway Key used from a browser is visible to that page's scripts**, and to anyone who can run script on that page or read its source. **Any origin** is safe in the sense that the key is the only credential, but the key is only as safe as every page it is put in. The Owner should give browser apps their own key, with Token Caps and only the AI Providers they need, and revoke it if a page is ever compromised; never a key with UI access.
- An origin in a key's list is `https://` and any host, or `http://` only for `localhost`, `127.0.0.1` and `[::1]`; no path or trailing slash, no wildcard, no `null`. It is kept as a browser sends it in `Origin` (lowercased, without a default port), each once. The server and the web form check it with the same schema (`keyBrowserAccessSchema`, `packages/shared`). It is kept in `gateway_keys.browser_access` (null for off).
