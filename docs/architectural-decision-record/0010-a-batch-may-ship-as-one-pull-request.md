# A Batch may ship as one pull request, its issues worked in turn on one branch

The Owner's daily habit is "complete issues 1 to 10 in one PR", but a Batch opened one pull request per issue (FR-21), each on its own branch. So a Batch may now be handed over "in one PR" (FR-25a): its issues are worked one at a time, in the Plan's order, on one branch, `ai-office/batch-<id>`, each building on the commits of the issue before it, and land in one pull request that closes them all. **Every Stage still works each issue on its own**: the work, review, QA and docs Stages, with the issue's own labels and Review Loop, reuse the per-issue flows as they are and only work on the Batch's branch, each issue's own work being what came after where the branch stood as it started (kept as its base, `batch_issues.base_sha`). The next issue starts once every issue before it is `ready-to-merge`. **The pull request is opened as the first issue goes to review** and written again as each joins it, in the `pr` Skill's shape (Summary, Evidence, Merge Danger), with `Closes #N` for each. **The Merge Policy considers it only once every issue is ready to merge**, asks of each what it asks of one issue's pull request, and holds the whole of it while any issue is with the Owner.

## Considered Options

- **Keep one pull request per issue**, and merge them as they come: no change, but not what the Owner does every day, and each issue's review waits for the one before it to merge.
- **A pipeline of its own for a Batch**, one Agent working all its issues in one sandbox run and one review of the whole: fewer runs, but a second pipeline beside the first, with no per-issue labels, Review Loop or caps, and a review of ten issues at once that no reviewer reads well.
- **The issues in parallel, each on its own branch, merged into one Batch branch**: keeps parallelism, but every merge into the Batch branch can conflict, and nobody reviews the merged result.
- **The per-issue pipeline, on one shared branch, one issue at a time** (chosen): every Stage, label and cap keeps its meaning, the change to the flows is which branch they work on, and each issue builds on the last without a merge between them.

## Consequences

- A one-pull-request Batch runs its issues one after another: it is slower than a Batch whose independent issues run in parallel. The Owner chooses it per Batch, by command; nothing else changes for other Batches. A chat request's Batch never goes in one pull request.
- The branch is named from the Batch alone, `ai-office/batch-<id>`, so every Stage finds it without reading an issue. The Branches page shows it as one lane, with the issue at work on it and where each of the Batch's issues stands.
- The shared branch is not rebased onto the default branch before review, unlike an issue's own (FR-25.5): a rebase would rewrite the commits earlier issues' reviewers approved. The pull request merges with a merge commit as ever; one that has come to conflict with the default branch is refused by GitHub and goes to the Owner, saying so.
- Each issue's reviewers see only its own diff, from its base, so they judge that issue; the docs Agent and designer read the same range, and QA tests the whole branch as it stands. An approval of an earlier issue counts for the head its work ended at (where the next issue began) or for the pull request's head; commits pushed on an issue after its reviewers approved send it back to them, as P1-1 asks of any pull request.
- The pull request's body is written by plain code from AI Office's own records (each issue's stage, review and QA rounds, and the files the pull request changes), not by a Model: its Summary is a tree of the issues and a sketch of the files, its Evidence before and after for each issue, and its Merge Danger a two-way door unless it changes database migrations.
- An issue handed to the Owner holds the whole pull request: the issues before it wait at `ready-to-merge`, those after it never start, and an action Notice says why. The Batch finishes when its pull request merges, or when the Owner closes or settles what holds it. "skip" and "move" change only the issues still to start; an issue that has started stays in the pull request.
- `pull_request.opened` is recorded for each issue as it joins the pull request, and `pull_request.merged` for each as it merges, so the Wrap-up and the Activity Feed tell each issue's story as before, with one pull request behind them all.
