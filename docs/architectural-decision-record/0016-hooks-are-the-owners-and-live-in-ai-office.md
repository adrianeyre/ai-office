# Hooks are the Owner's and live in AI Office

The Owner wants rules of their own on a Floor that act on events: "when a pull request touches migrations, have the reviewer run `/migration-check`". Until now the event bus drove only AI Office's own steps and the Communications Agent's fixed toggles. A Hook is a rule with a trigger, optional filters and an action: when an issue moves to a Stage, a pull request is opened, a push to the default branch touches matching files, a Batch's Wrap-up is given, a Spec's issues are filed, or the Owner presses **Run now**, a named Agent (or any Agent in a named Role) runs one Skill of the Floor's library, given the event's details. Guidelines live in the repository and reach Agents only as the Owner approved them (ADR 0014); a Hook could have lived there too, beside the code it watches. But a Hook is not text an Agent reads: it is a standing order that spends tokens and acts on every event that matches, with nobody in the loop. So **Hooks are kept in AI Office's database, made, changed and deleted only by the Owner**, in the Floor admin's **Hooks** card and its API, and included in configuration export like the Floor's other settings.

## Considered Options

- **Files in the repository** (`.agents/hooks/*.yml`), approved like Guidelines: versioned and reviewed with the code, but every push would be one more thing for the Owner to approve, and a Hook that slipped through would spend the Owner's tokens on its own schedule. The approval machinery of ADR 0014 would need a second, stricter copy for something no Agent needs to read.
- **Shell commands on events**, as a coding assistant's hooks or a git hook run: the most flexible, but a command run by AI Office on a trigger anyone who opens a pull request can set off is remote code execution waiting for a mistake, outside every sandbox and the AI Gateway. The PRD rules it out.
- **Agents or the Manager adding Hooks**: a Manager could set up Hooks of its own from a chat request. But a model would then decide what runs on every later event, as a model accepting Role memory would (ADR 0005), and one hostile issue could leave a rule behind that outlives it.
- **In AI Office, the Owner's alone, and a run is one Skill followed by one Agent through the Gateway** (chosen).

## Consequences

- **Only the Owner makes or changes a Hook.** The Hooks routes need the Owner's session (a password, or an API key with UI access); no Agent, Manager chat turn, Skill or Connection reaches them. Every change (added, changed, turned off, deleted) is an event in the Activity Feed, `hook.added`, `hook.changed` and `hook.removed`, and so is every run, `hook.run_started`, `hook.run_finished` and `hook.run_skipped`.
- **A run is one model call, made as the Agent**, as a reviewer's is (FR-20): through the AI Gateway with that Agent's own Gateway Key, so it is attributed to it and counts against its Token Caps (FR-32), and a cap it has reached refuses it. Its system prompt holds the Skill's instructions, which are trusted input like every Skill (FR-76). The event's details (the issue's title and labels, the pull request's changed files, the push's commits) go in the user turn as **untrusted data**, between `<event>` markers it cannot close. No sandbox is started and nothing is run: **no shell commands**, no clone, no push.
- **What a run says is posted, never acted on.** The Agent's answer is redacted and posted by the GitHub App as a comment on the issue or pull request the event names, and kept with the run, which the Hooks card shows. Nothing AI Office reads as an instruction comes out of a run, so a run cannot move an issue, merge, file an issue or change a Hook.
- **A Hook never fires on an event its own run caused.** The chain of Hooks whose runs led to an event is carried with it through the event bus; a Hook in that chain is not run for it. Another Hook may be, within its own limits.
- **Limits bound every Hook.** At most 12 runs an hour by default, settable per Hook (1 to 60); never two runs of one Hook at once on the same issue or pull request, the second being skipped; a pull request opened runs a Hook once, however many issues join it (ADR 0010). A failed run raises an info Notice; three failed runs in a row turn the Hook off with an action Notice, until the Owner turns it on again.
- **Hooks name things that may go.** A Hook that names an Agent no longer on the Floor, a Role with no Agent free, or a Skill the Floor no longer has fails when it runs, saying so, and counts toward turning it off. An import brings Hooks with the Floor; their Skills are checked when they run, since a repository Skill can only be read from GitHub.
- A Floor without Hooks behaves exactly as before.
