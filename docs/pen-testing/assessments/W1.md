## Verdict in one line

**H12 is CONFIRMED, and is no worse than the register said.** A captured
delivery is acted on every time it is sent (W1-1). But a delivery only
says *when* to look. Every state it can reach (merge, intake, labels,
close) reads GitHub again, so no replay merges a pull request, takes in
an issue or moves a label that GitHub does not already say should be.
The signature holds as the PRD says: HMAC-SHA256 over the raw bytes,
compared in constant time, and nothing is believed without it.

The App's write path holds where it matters most. Nothing an Agent
controls chooses the branch, the repository or the ref the App pushes,
and auto-merge names the head CI passed on. Two things around it are
weaker than the documents say:

- **W1-6:** the Owner's **Approve and merge** merges whatever the branch
  holds when it is clicked.
- **W1-3:** one read-only token serves every sandbox of a Floor and is
  never revoked.

The rest is hygiene:

- **W1-2:** the App's own tokens ask GitHub for no narrower permissions.
- **W1-4:** nothing limits deliveries.
- **W1-5:** an Agent's own trailers reach commits authored as the Owner.

## How this was exercised

Everything ran against the real code, with the fake GitHub standing in
for GitHub:

- **The route:** the real Fastify app (`buildApp`) through `inject`, with
  real intake polling the fake GitHub over two Floors. Each delivery was
  signed or forged byte for byte, as a spoofed GitHub sends it.
- **The receiver:** the real `createGitHubWebhooks`, put in front of the
  real Merge Policy flow (`createMergeFlow`). The flow was left waiting
  for CI on an auto-merge Floor whose required reviewer had approved, and
  deliveries were replayed in each state of that wait.
- **Tokens:** the real `createGitHubApp` minted from the fake GitHub
  served over HTTP (`serveFakeGitHub`). It records what each
  `POST /app/installations/{id}/access_tokens` asked for.
- **The write path:** the real `createPushRun` (`publishBranch`) pushed,
  with a writing token, from an Agent clone the test made hostile to a
  local bare repository standing in for the Floor's.
- **Approve and merge:** the real merge flow and Notices ran against the
  fake GitHub, which refuses a merge whose expected head is not the pull
  request's, as GitHub does.

## Verdict on every "What to probe" bullet

### Signature: HMAC-SHA256 over the raw body, constant-time; missing or malformed header; secret unset

**HOLDS** on every part (PRD "Confirm, don't re-test": the HMAC
comparison is constant-time).

- **Over the raw body.** The delivery route is its own Fastify scope.
  There every content-type parser is removed and one catch-all keeps the
  body as a `Buffer` (`apps/server/src/webhooks/routes.ts`), so nothing
  parses the body before it is verified.
  - A pretty-printed body signed as sent is taken under every content
    type: `application/json` with or without a charset, `text/plain`,
    `application/x-www-form-urlencoded`, `application/octet-stream`, and
    none at all.
  - The same JSON under the signature of its compact form is refused
    (401) under each of them.
  - Bytes that are not UTF-8 verify only as sent, never as their lossy
    text.
- **HMAC-SHA256, constant time.** The signature is `sha256=` and the hex
  HMAC-SHA256 of the bytes with the secret, as GitHub makes it.
  - It is compared with `timingSafeEqual`. A test spies on it, so a
    change to `===` fails.
  - A header that is not `sha256=` and 64 hex digits is refused before
    any comparison. So the only thing an early refusal says is the
    header's format, never a prefix of the right answer.
  - The two sides compared are always 71 bytes, so `timingSafeEqual`
    never throws.
- **Missing or malformed header.** Each of these is refused with 401 and
  starts nothing:
  - no header, an empty one, or `sha256=` alone;
  - `sha1=…`, or one hex digit short;
  - a signature made with a guessed secret;
  - the header sent twice (it arrives as an array, which is read as
    none).

  Upper case and surrounding whitespace are accepted: the same signature,
  not a weaker one.
- **Secret unset.** With no secret kept, or webhooks off, the route
  answers 404 before anything is read, even to a delivery signed with
  the empty secret. `verifyWebhookSignature` refuses everything while the
  secret is empty. The settings refuse a secret shorter than 20
  characters, and the secret is sealed at rest for its own field
  (`office_settings.github_webhook_secret`).
- **Not a finding:** the route answers 404 while webhooks are off and 401
  to a bad signature once they are on. So an unauthenticated caller can
  tell which it is. `setting-up-a-floor.md` documents both answers, and
  they say nothing of the secret.

### Replay: each state in which a replayed delivery is not a no-op (merge, intake, label, close)

**FINDING (W1-1), H12 confirmed. What a replay can change, HOLDS.**

Neither the body nor `X-GitHub-Delivery` is remembered. The id is read
only for the log line, and GitHub signs only the body, so the id is the
sender's to choose. One captured delivery can be sent again, under its
own id, a new one or none, as often as wanted. It is believed and acted
on each time, with no time bound: GitHub signs no timestamp, so a
delivery stays good until the secret changes.

Here is what each replay does in each state:

| State | What a replay starts | What it can change | Verdict |
|---|---|---|---|
| **Merge** (a pull request at `ready-to-merge` on an auto-merge Floor, the gate waiting for CI) | `check_run`, `check_suite` or any `pull_request` action but `closed`: the gate looks at CI again now | Nothing GitHub does not say. The gate reads the pull request and its check runs from GitHub at each look. A "passed" check run replayed five times while CI runs merges nothing. Replayed after CI failed, it sends the pull request to the Owner. Once CI passes, the App merges once, naming the head CI passed on. A replay after the merge reaches nothing | holds |
| **Intake** (an issue opened, reopened, labelled, edited or transferred) | An intake round over **every** Floor, not only the one the delivery names | Nothing GitHub does not say. Intake reads the issues and who labelled them from GitHub, so it ignores a signed delivery claiming the Owner as sender of a stranger's label, an unlabelled issue or one that does not exist. A replay after the Owner took the label off takes nothing in. An issue already in the pipeline is not taken in twice. By reading: the Manager's triage keys on the issue's text (`issueFingerprint`), so a replay never makes a second model call | holds; the cost is W1-1 |
| **Label** (a pipeline or `role:` label deleted or renamed) | That Floor's labels are checked and made again in the next round, then an intake round | The labels GitHub should have anyway; `ensureLabel` is idempotent | holds; the cost is W1-1 |
| **Close** (an issue or pull request closed) | The Batches' check | It reads its Batches from the store and their issues from GitHub. A replay starts nothing whose dependencies are not done on GitHub | holds |

So a replay is a no-op in effect. It is **not** a no-op in cost:

- each replayed issue delivery runs a full intake round, listing every
  Floor's issues with each Floor's installation token;
- rounds coalesce only while one runs, so replays sent one after another
  each get a round.

Pinned in `routes.pen-test.test.ts`, "W1-1": five replays, five rounds,
five `listIssues` on each of two Floors. Pinned also in
`webhooks.pen-test.test.ts`, "replaying a CI delivery while the Merge
Policy waits for CI". Exhausting GitHub's rate limit this way was not
exercised: denial of service is out of scope.

### Event types and actions handled; anything acted on without checking the installation and repository match a Floor

**HOLDS**, with one thing to know.

- **What is handled** is exactly this table (`webhookActions`). Every
  other event and action starts nothing, among them `push`,
  `installation`, `installation_repositories`, `member`, `repository`,
  `label.created`, `issues.deleted`, `issues.assigned` and `ping`.

  | Event | Action | Starts |
  |---|---|---|
  | `issues` | `opened`, `reopened`, `labeled`, `edited`, `transferred` | intake |
  | `issues` | `closed` | the Batches' check |
  | `label` | `deleted`, `edited`, for a pipeline or `role:` label | the Floor's labels again, then intake |
  | `pull_request` | `closed` | the Batches' check |
  | `pull_request` | any other | the Merge Policy's look at CI |
  | `check_run`, `check_suite` | any | the Merge Policy's look at CI |

- **The repository** must name a Floor in use (case-insensitively, so
  archived Floors are left out). A signed delivery about any other
  repository is answered 202 and starts nothing.
- **The installation is never read.** `parseWebhookPayload` reads the
  action, `repository.full_name` and the label's name, nothing else: no
  installation, sender or issue. A signed delivery naming another
  installation's id, about a repository named as a Floor's, starts that
  Floor's rounds (pinned).

  This is not a finding, because nothing is acted on from the payload.
  Each round reads GitHub through the Floor's own installation,
  `GET /repos/{owner}/{repo}/installation`. Intake's and the Batches'
  rounds run over every Floor whichever one a delivery names, so matching
  the installation would change only which deliveries start a round. The
  webhook secret is the App's, one for all its installations. The setup
  guide has the App installable "Only on this account", so no other
  account's installation can sign one.

### Installation tokens: permissions and repositories at mint time; lifetime; where held; the sandbox's read-only token is read-only

- **The sandbox's token: HOLDS.** `readOnlyToken()` mints for the Floor's
  repository alone (`repositories: ["web-shop"]`), with `contents`,
  `issues`, `pull_requests` and `checks` each `read`. S2 drove what it
  can then do against the fake GitHub: it reads the issue, and is refused
  (403) a comment, an issue, a pull request and a ref. It reads nothing
  of another repository in the same installation. The token that writes
  is never the token a sandbox is given: they are separate mints under
  separate cache keys.
- **The App's own tokens' permissions: FINDING (W1-2).** Both of the
  App's own tokens leave `permissions` out of the mint, so GitHub gives
  each **every** permission the installation was granted:
  - `installationToken()`, the token that pushes, merges, labels and
    comments;
  - the token `repositories()` uses to list them.

  The guide's table (`appPermissions`) is enforced only by how the Owner
  registers the App. If the Owner grants more, such as **Workflows**,
  which the guide offers, or anything granted by mistake, AI Office's
  tokens carry it too.
- **Repositories: HOLDS for the tokens that act**, each minted for one
  repository. **FINDING (W1-2)** for the listing token: it asks for no
  repositories, so it covers every repository of the installation, with
  every permission. It is kept for 55 minutes.
- **Lifetime: FINDING (W1-3).** Each token is GitHub's hour, kept and
  handed out until five minutes before it expires
  (`createTokenCache`), then replaced. So the one read-only token of a
  Floor is handed to every sandbox, Manager chat session and fact-finding
  run that starts in those 55 minutes. A sandbox can be given one minted
  54 minutes earlier, for another.
  - Nothing ever revokes a token: there is no
    `DELETE /installation/token` on the client, and no call to one.
  - A token a sandbox sends out (it has open egress, S2-1) still reads
    the Floor's private repository, its issues and its pull requests for
    up to an hour after the sandbox has gone.
  - It cannot be told from the token every other sandbox of the Floor
    was given.
  - `setting-up-a-floor.md` says "each sandbox gets its own short-lived
    installation token". It does not.
- **Where held: HOLDS (read, and pinned in part).**
  - Tokens are held in the server's memory only (`createTokenCache`'s
    `Map`), never in the database, an event or a Notice.
  - The token that writes reaches Git only through the environment of
    Git's own process (`GIT_CONFIG_*` in `git/command.ts`). That is in
    AI Office's own scratch repositories (`publishBranch`,
    `commitFile`), never in the command line, a repository's config or a
    sandbox.
  - The read-only token reaches a sandbox as `GH_TOKEN` (S2), and the
    clone through the environment (PRD "Confirm, don't re-test": clone
    tokens).
  - Octokit's own errors carry `authorization: [REDACTED]`, as seen in
    this probe's own failing runs.

### The App's write path: can anything an Agent controls choose the branch, repository or ref the App pushes or merges?

- **The branch: HOLDS.** It is `issueBranch(issue, title)`, from the issue
  as GitHub has it. Sandcastle's `branch` strategy returns the branch it
  was given, and the Agent has no way to name another.

  Whatever the title says, the branch is `ai-office/<issue>`, optionally
  with `-` and a slug of `[a-z0-9-]`, 40 characters at most. That held
  for `main`, `../../main`, `refs/heads/main`, `:refs/heads/main`,
  `+main:main`, `HEAD`, a right-to-left override, full-width letters,
  `-` and 500 characters. It is never another issue's branch,
  `ai-office/memory` or `ai-office/grilling-<n>`.
- **The repository: HOLDS.** The push URL comes from the Floor's
  repository as GitHub describes it (`client.get()`), never from the
  clone.
- **The ref pushed: HOLDS.** `publishBranch` fetches `refs/heads/<branch>`
  alone from the clone into a fresh bare repository of AI Office's own,
  then pushes `<sha>:refs/heads/<branch>` to that URL. The test set up a
  hostile clone that:
  - moved its `main` and tagged it;
  - made `ai-office/2-…` and `ai-office/memory` branches;
  - pointed `origin` at another repository, with
    `remote.origin.push=+refs/heads/*:refs/heads/*`, `remote.pushDefault`,
    `push.default=matching`, `branch.<b>.pushRemote` and
    `branch.<b>.merge=refs/heads/main`.

  After the push the Floor's repository has exactly its `main`, as it
  was, and the issue's branch. The other repository is untouched. By
  reading, not exercised here: a push that would replace commits GitHub
  has and the Agent did not build on is not forced (`rebase` returns
  undefined), so GitHub refuses it.
- **What is in the commits: FINDING (W1-5).** Each commit is made again
  as the Owner, with the Agent's trailer (FR-68, FR-69). That holds
  against a commit the Agent authored as anyone. But its message is kept
  as the Agent wrote it, so trailers the Agent writes are pushed into
  commits authored as the Owner:
  - `Agent: Grace (reviewer, ChatGPT gpt-5)`, naming another Agent;
  - `Co-authored-by: <anyone>`, which GitHub shows as a co-author.

  So is the author date it chose. The Agent's own trailer is added last,
  so history cannot be relied on to say which Agent made a commit.
- **The ref merged by policy: HOLDS.** Auto-merge passes GitHub the head
  CI passed on (`sha`). The test pushed work to the branch just as the
  App merged. GitHub refused the merge (409), nothing reached `main`,
  and the pull request went to the Owner. What else the gate merges is
  P1-1 (#194).
- **The ref merged on the Owner's approval: FINDING (W1-6).** **Approve
  and merge** calls `mergePullRequest(number)` with no `sha`, so GitHub
  merges whatever the branch holds when the Owner clicks. The guide says
  it merges "as the Owner approved it". The Notice is raised once per
  pull request (`raiseOnce`) and, by reading, nothing closes it when the
  issue leaves `ready-to-merge`: the only Notice AI Office dismisses
  itself is triage's. So if the issue goes round again, the stale Notice
  merges the newer head, unreviewed if the Owner clicks before review
  ends. The same happens to anything else pushed to the branch since the
  Owner looked, including an Agent's later work pushed by the App.
  Pinned: a head pushed after the Notice is merged on the click.

### Why these severities

- **W1-1, low (as the register said):** a replay changes nothing GitHub
  does not already say, since the payload decides only when AI Office
  looks. What it buys an attacker is cost: GitHub API calls on every
  Floor's installation, up to its rate limit. That would stall intake,
  pushes and merges until the hour resets (not exercised: DoS is out of
  scope). It needs a captured delivery, whose sources are GitHub's
  **Recent Deliveries** (the Owner's), a TLS-terminating proxy in front
  of AI Office, or a body logged on the way.
- **W1-2, low:** the Owner's App registration is a recorded control
  (`setting-up-a-floor.md` and the test that keeps its table and
  `appPermissions` equal). Nothing an attacker does widens it. Narrowing
  at mint time is depth for the day a token leaks from the app (H1,
  H16) or the Owner grants more than the table.
- **W1-3, medium:** the guide claims a token per sandbox, and the one
  boundary that would bound a leaked token, revocation or a short life,
  is absent. Not high: it reads only the one repository, which the
  sandbox can read and send anyway (S2-1).
- **W1-4, low:** absence of a rate limit. Each forged delivery costs a
  database read, an AES-GCM open, one HMAC over at most 5 MiB and a log
  line. It was exercised to 200 deliveries, not beyond.
- **W1-5, low:** FR-68 holds (the author and committer are the Owner),
  and FR-69's trailer is there. The Agent can only add misleading lines
  beside it, which is disclosure and hygiene, not access.
- **W1-6, medium:** the Owner's approval is the control a "send to me"
  Floor (the default) relies on, and the guide says the App merges "as
  the Owner approved it". It needs work pushed between the Owner's
  reading and the click: the issue going round again with the Notice
  still open, or anyone else who can push to the branch. Not high,
  because the Owner is still asked; what is merged differs from what was
  asked about.

### What each fix must make true (for the remediation issues; not how)

- **W1-1:** A delivery whose signed body AI Office has already taken
  starts nothing, whatever `X-GitHub-Delivery` it carries. GitHub's own
  **Redeliver** of a delivery that was not taken still works. A delivery
  about one Floor costs no other Floor a round.
- **W1-2:** Every installation token AI Office mints asks for the
  permissions its use needs and nothing more: `appPermissions` for the
  App's token, metadata alone for listing. Each covers only the
  repositories that use needs.
- **W1-3:** Each sandbox (and each Manager chat session and fact-finding
  run) gets a read-only token of its own, which stops working when that
  sandbox stops. The guide says what is true.
- **W1-4:** Deliveries that fail the signature check from one client are
  refused before they are verified once past a bound, and their log
  lines are bounded too. GitHub's own deliveries are never refused for
  it.
- **W1-5:** A commit the App pushes names in its trailers only the Agent
  AI Office says made it. No `Agent:` or `Co-authored-by:` trailer the
  Agent wrote survives as one.
- **W1-6:** **Approve and merge** merges only the head the Owner was
  asked about. If the branch has moved since, nothing is merged and the
  Owner is asked again about the new head. A Notice whose pull request
  has left `ready-to-merge` offers no merge.

## Could not be exercised here, and what would

There is no GitHub and no Docker here, and the fake GitHub stands in for
both GitHub's REST API and its webhooks. On the pen-test stack, with its
own App and installation:

- **W1-1:** take one delivery from the App's **Recent Deliveries**, as
  the red team's position-5 harness would hold it, and send it twice to
  `/api/github/webhooks` with `curl`, the second time with a new
  `X-GitHub-Delivery`. Both answer 202, and the server logs two
  "A GitHub webhook delivery was taken." lines and two intake rounds.
  Also confirm what GitHub's **Redeliver** sends for `X-GitHub-Delivery`
  (the same GUID or a new one), which the fix must allow for.
- **W1-2:** on GitHub, a token minted with no `permissions` carries the
  installation's granted permissions; the fake gives it `appPermissions`.
