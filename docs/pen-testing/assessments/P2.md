## Verdict in one line

**H18 is CONFIRMED.** "Read-only" bounds the session's tools by command
*prefix*, not by effect: an allowed `git diff` reads any file in the
container — including the Manager's Gateway Key at `/proc/self/environ` —
and `WebFetch` sends it out (P2-1), and an allowed `git diff`/`git log`
writes any file the container's filesystem permits, including the
persistent tool-home mount (P2-2). A chat Batch files issues, adds
Contractors and starts work on one Model decision, with no Owner approval
(P2-3), and a one-off Contractor Role's instructions — free text the Model
writes in the turn it read attacker content — reach a work-Stage Contractor
verbatim, enabled without review (P2-4). What holds: the clone is mounted
read-only, so the session cannot write its own `.git`, and the host-side
refresh runs none of a hostile `.git`'s programs (the S1 fix covers the
Manager's clone); the environment carries no GitHub token and no AI Account
credential, only the Gateway Key; the Manager's authority is confined to
filing issues and adding or releasing Contractors; `@` mention path checks
hold; attachments are served inert and isolated to their Floor; a
Manager-filed issue enters work only through its Batch.

## How this was exercised

- **The session's flags and their effect.** The real `claudeSessionArgs`,
  `claudeAllowedTools` and `claudeSessionTools` were read, and a model of
  Claude Code's prefix matching (`Bash(<prefix>:*)` permits a command
  beginning `<prefix>`) was applied to the commands `git diff --no-index`,
  `git diff --output` and `git log --output`. Real `git` (2.39.5) was then
  run in a temporary repository to show `--no-index` prints a file outside
  the repository and `--output` writes a file. The real
  `gatewayModelEnvironment` and `codexModelEnvironment` were driven to pin
  that the Gateway Key is in the environment the session container receives.
- **Injection to action.** The real `createChatRequests().batch()` was
  driven with a `batch` decision carrying a one-off Role whose instructions
  hold an injection, against recording doubles for the agents, issues,
  batches and work stores. It files the issue, adds the Contractor with the
  instructions verbatim, and starts the Batch, with no approval anywhere in
  the path. The real `assertManagerMayForChat` and `managerGitHub` were
  driven to confirm the authority limits.
- **Host-side git on the read-only clone.** The real `dockerSessionTool`
  was driven against a local bare repository and a fake tool runner. A
  hostile `core.fsmonitor`, `core.hooksPath` and `post-commit` hook were
  planted in the host clone, and a second turn's `refresh` (`git fetch`
  then `git reset --hard`) was run; none of the planted programs executed.
- **Attachments and mentions.** The real Fastify app (`buildApp`, two
  Floors, memory stores, fake GitHub) served an XML attachment holding
  script markup and a cross-Floor fetch. The real `createChatRepositoryFiles`
  was driven with traversal, absolute and `.`-segment paths.

No production code was changed. Probe tests:

## Verdict on every "What to probe" bullet

### Read-only, really?

- **Write a file: FINDING (P2-2), H18.** Claude Code's only Bash allow-rules
  are `Bash(git log:*)`, `Bash(git show:*)` and `Bash(git diff:*)`, matched
  by command prefix. `git diff --output=FILE` and `git log --output=FILE`
  both begin an allowed prefix and both write a file. The clone mount is
  read-only, so a write *to the clone* fails, but the container's root
  filesystem is writable (S2-4) and the tool-home mount
  (`/home/agent/.claude` or `.codex`) is read-write and persists across
  turns and restarts, so a "read-only" session writes a persistent file.
  Pinned in `agent-tool-session.pen-test.test.ts`, "P2-2".
- **Run a command beyond `git log|show|diff`: FINDING (P2-1), H18.** The
  prefix rule does not bound what git then does. `git diff --no-index
  <path> <path>` reads any two files on the container's filesystem — it is
  not confined to the repository — and prints them into the diff the
  session reads. Real git confirms it prints a file outside the repository.
  Combined with `/proc/self/environ` (which holds the Gateway Key) and the
  read-only clone (the Owner's private source), and `WebFetch`/`WebSearch`
  in the allowed tools, this is a read-and-exfiltrate path. Options such as
  `--ext-diff`, `-O<file>`, `-c`, pagers and aliases were considered: they
  need config the read-only clone does not carry (git config is not a
  repository file, and the clone's `.git/config` is AI Office's own), so
  `--no-index` and `--output` are the exercised vectors. Pinned in
  "P2-1"/"P2-2".
- **Reach MCP or settings from the repository: HOLDS.** Claude Code is run
  with `--setting-sources user` (project and local settings are not read),
  `--strict-mcp-config` (no repository `.mcp.json`), `--permission-mode
  dontAsk` and an explicit `--disallowedTools` of Edit/Write/MultiEdit/
  NotebookEdit. So `.claude/settings.json`, `.mcp.json` and
  `.claude/settings.local.json` in the clone widen nothing. Codex is run
  `--sandbox read-only` with `approval_policy="never"` and its config on
  the command line; its `$CODEX_HOME` is the read-write tool home, not the
  repository's `.codex/`. Codex does read `AGENTS.md` from the working
  directory as instructions — that is the injection vector of this probe,
  not a settings escalation. Pinned by the flags in
  `agent-tool-session.pen-test.test.ts` and
  `chat-sessions.test.ts` (existing).
- **Is the clone mount read-only, and is anything else mounted: HOLDS.**
  The clone is mounted `readOnly: true` at `/home/agent/workspace`; the
  tool's home is mounted read-write (its sessions persist, by design); a
  turn's images are mounted read-only and removed after. Nothing else is
  mounted; no GitHub token and no Docker socket. Pinned in
  `chat-sessions.pen-test.test.ts` and `chat-sessions.test.ts` (existing).

### Injection to action

- **Can hostile content make the Manager file issues, add Contractors,
  write a Contractor Role that carries the injection on, or start a Batch,
  with no Owner approval: FINDING (P2-3, P2-4), H18.** A chat turn runs the
  Manager's agent session (Claude Code/Codex), which reads attacker content
  through its own tools — repository files (Read/Grep/Glob), fetched web
  pages (WebFetch), `AGENTS.md`, attachments and `@` mentions. The *same*
  session's reply, if it opens a ` ```request ` block, is parsed by
  `parseChatRequest` and carried out at once by `requests.batch()`: issues
  filed, Contractors added, a Batch started (`chat.ts` `carryOutReply` →
  `requests.batch`). No approval step stands between the Model's decision
  and the work; ADR 0004 makes this deliberate ("the request standing as
  the Plan's approval"), but nothing binds the Batch to the Owner's literal
  request rather than to content the session read, and the untrusted-data
  fencing (`chat-turn.ts`) wraps only the turn's attachments and mentions —
  not what the session reads with its tools. P2-3 pins that one decision
  files and starts work with no approval. P2-4 pins that the one-off Role's
  `instructions` reach `agents.addContractor` verbatim, enabled without
  review, so the injection carries into a work-Stage Contractor;
  `oneOffRoleSchema` checks only the name's shape and length, not the
  instructions' content. This contradicts ADR 0003 ("imported Roles ... are
  reviewed before they are enabled"): a Manager-written one-off Role is
  never reviewed by the Owner. Pinned in `requests.pen-test.test.ts`,
  "P2-3" and "P2-4".
- **Is the Owner's request the only thing that can start a chat Batch: NO**
  (part of P2-3). The Model's decision drives the Batch, and the Model is
  steered by everything the session reads. The exercise of the final
  injection-to-decision step needs a live model and is listed under "Could
  not be exercised here".
- **Does a Manager-filed issue enter work only through its Batch (ADR
  0004): HOLDS.** `managerChatIssues.file` labels the issue `ai-office`
  only. Intake takes in only issues the Owner opened or labelled
  (`fromOwner`); a Manager-filed issue is authored by the GitHub App, not
  the Owner, so intake ignores it. The Batch reaches its own just-filed
  issues through the `filed` set that `batches.create` is given, not through
  intake. If the Batch fails to start after filing, the issues sit ignored
  until the Owner says "complete issues …"; they do not enter work on their
  own.

### Authority limits

**HOLDS** (`requests.pen-test.test.ts`, "the Manager's authority limits
hold"). `assertManagerMayForChat` permits only `file_issue`,
`add_contractor` and `release_contractor`; `merge`, `raise_cap` and
`change_repository_settings` are refused. `managerGitHub` refuses merge,
creating an issue, write and read-only tokens, branch and label changes and
reviews; reads pass through. Contractors are added only within the Floor's
"most Agents" and the sandbox limits (`contractorRoom`, `staff`), never with
Token Caps of their own, and the prompt forbids naming an Agent, a Model or
a cap. None of merge, a settings change or a cap raise can be passed through
the chat. (A one-off Role's *instructions* are free text, P2-4, but the
Contractor they configure holds a read-only token and cannot merge or push
itself; what such a Contractor does inside the work Stage is #194.)

### Exfiltration

**FINDING (P2-1), H18.** The session can read the read-only clone (the
Owner's private source), a turn's attachments, and its environment — which
holds the Manager's Gateway Key (`ANTHROPIC_AUTH_TOKEN` for Claude Code,
`AI_OFFICE_GATEWAY_KEY` for Codex) readable at `/proc/self/environ` via
`git diff --no-index`. `WebSearch` and `WebFetch` reach any host. So a
steered session can send the private source and the Gateway Key out until
the key is revoked. What it cannot steal: there is no GitHub token in the
session's environment (`githubToken: ""`), and no AI Account credential
(refused by shape and value). Pinned in `agent-tool-session.pen-test.test.ts`.

### Attachments

**HOLDS** (`routes.pen-test.test.ts`, and `routes.test.ts` existing).

- **Size and type against the real bytes:** images are checked by magic
  bytes (`looksLike`), the size is taken from the decoded bytes (5 MiB
  image, 1 MiB text), and SVG and HTML are not allowed media types.
- **`GET …/attachments/:id`:** an image is served inline with its own
  content type; a text file is served `Content-Disposition: attachment`
  (a download) with `charset=utf-8`; both carry `X-Content-Type-Options:
  nosniff`, `Content-Security-Policy: default-src 'none'; img-src 'self';
  sandbox` and `Cross-Origin-Resource-Policy: same-origin`. An XML
  attachment holding `<script>` is served as an inert download, not a page,
  so there is no stored XSS through an SVG or HTML upload.
- **Access across Floors:** `get(floorId, id)` is scoped to the Floor; an
  attachment of one Floor returns 404 through another Floor's URL, even for
  the Owner. The route is `access: "owner"`.
- **Retention:** unsent attachments are deleted after a day
  (`deleteUnsentBefore`).
- **The image path inside the container (`sessionImagePath`):** the name is
  stripped of non-word characters and leading dots and sliced, so an
  attachment name cannot traverse out of the mounted attachments directory.
- **Note (not a finding):** a *text* attachment's bytes are checked only to
  be UTF-8, not to be the declared type (a `application/json` upload holding
  HTML is accepted). FR-24 says each is "checked to be what it says"; for
  text that is weaker than the words, but it is safe because the serving
  headers make the content inert and the text reaches the Model fenced as
  untrusted. Pinned in `routes.pen-test.test.ts`.

### `@` file mentions

**HOLDS** (`repository-files.pen-test.test.ts`). `readable` rejects an
empty path, an absolute path, and any path with a `.` or `..` segment, so a
traversal reads nothing and never reaches GitHub. Mentions are read through
the GitHub App against the Floor's own repository at its default branch —
not the local clone — so a symlink planted in the clone cannot redirect a
read, and one Floor's mention cannot read another's. At most 10 files, 200
KiB each.

### Host-side git on the Manager's read-only clone

**HOLDS** (`chat-sessions.pen-test.test.ts`). The clone is mounted
read-only into the session, so the session cannot write its `.git` to
begin with. As defence in depth, with a hostile `core.fsmonitor`,
`core.hooksPath` and `post-commit` hook planted in the host clone, the
`refresh` that runs before each turn (`git fetch`, `git reset --hard`,
through `runGit`) executed none of them: no marker file appeared. The S1
fix (`runGit` neutralisation, #186/#201/#203) covers the Manager's clone.

### Why these severities

- **P2-1 high:** a sandbox/Gateway-Key boundary is crossed. The Gateway Key
  spends the Owner's AI Accounts until revoked, and the private source
  leaves the Office. The only control was "the session is read-only", which
  does not hold.
- **P2-2 medium:** the "read-only" boundary is undefended in depth — the
  session writes, but to its own tool home and the container, not to the
  clone or the host; its impact is persistence of session-side state, not a
  change to the repository.
- **P2-3 high:** a control (Owner approval of what runs) holds in no layer
  for a chat Batch; injected content, not the Owner, can start work that
  runs and, by Merge Policy, lands. Rated against the deliberate ADR 0004
  design, for which no control records that only the Owner's intent drives
  the Batch.
- **P2-4 high:** the injection crosses from the chat into a work-Stage
  Agent's Role instructions, which ADR 0003 treats as trusted and requires
  to be reviewed before enabling; a Manager-written one-off Role is enabled
  with no review.

### What each fix must make true (for the remediation issues; not how)

- **P2-1:** The Manager session's shell can run only genuinely read-only
  git history commands; it cannot read a file outside the read-only clone,
  and in particular cannot read the process environment or the Gateway Key.
  (Or the Gateway Key is not reachable from the session's filesystem/env.)
- **P2-2:** The Manager session cannot write any file anywhere in its
  container, including the tool-home mount, through an allowed command.
- **P2-3:** A chat Batch runs only work the Owner authorised: content the
  session reads cannot, by itself, cause issues to be filed, Contractors
  added or a Batch started. The control that ties a Batch to the Owner's
  own request is recorded.
- **P2-4:** A one-off Contractor Role's instructions cannot carry an
  injection from chat content into a work-Stage Agent without a review step,
  as ADR 0003 requires for Roles that reach models.

## Could not be exercised here, and what would

- **The injection-to-decision step itself** needs a live model: that a
  hostile repository file, fetched page or attachment steers the Manager's
  Model to emit a `batch` (or `research`) decision. The mechanism after the
  decision — no approval gate, verbatim one-off Role instructions — is
  pinned deterministically. On the pen-test stack, position 2 (a target
  Floor seeded with the hostile-content corpus, E2) would drive a real
  Claude Code/Codex session and show a planted instruction producing a
  filed-and-started Batch.
- **The container-side reads and writes** (`git diff --no-index
  /proc/self/environ`, `--output` into the tool home) were shown with real
  git on this host and with the flags and environment AI Office passes;
  they were not run inside a live Claude Code session in a Docker sandbox.
  On the stack, position 3's harness would run them from inside the
  Manager's session image.
- **WebFetch egress** reaching a red-team host is S2-1's exercise; here only
  that `WebFetch` is an allowed tool was pinned.

## Out of scope here

- Injection into the work Stages' Agents, memory, CI and the Merge Policy:
  #194 (P1). What a one-off Role's Contractor then does in the work Stage is
  P1's, not this probe's.
- Gateway Keys and Token Caps at the Gateway: #195. P2-1 shows the key can
  be read and sent; what it can do there is #195.
- Sign-in and sessions (a stolen session driving the chat, position 4):
  #192. This probe assumes the session is reached; it does not test
  obtaining it.
- Sandbox run flags, egress and reach (S2): the writable container root and
  open egress that make P2-1/P2-2 reach out are S2-4 and S2-1.
