## Verdict in one line

**H21 is CONFIRMED on both halves, and the split itself holds.** The one
entry point routes `/v1` to the Gateway before any of the app's hooks, and
it routes cleanly: path confusion (`//v1`, `/V1`, `/v1/../api/…`,
percent-encoding), a session cookie, and a cross-origin preflight all stay
on the side they should, and a presented Gateway Key never reaches an AI
Provider or a log line. But the app-wide controls do not reach `/v1`,
because nothing of the app does: a hook-set security header never fires for
`/v1` (I2-1), an unauthenticated request's body is read in full before it
is refused (I2-2), and Gateway Key guesses at `/v1` are neither limited nor
recorded, unlike sign-ins (I2-3). Under compose the `sandbox-dir` service
runs `mkdir -p` and `chown` as root on a path under the world-writable
`/tmp`, with no symlink-safe or ownership check, so a local user who gets
there first has the root `chown` follow their symlink and the app's clones
land where they chose (I2-4); and the work directory is created `0755`, so
any local user or bind mount reads every Floor's clone beneath it (I2-5).
The `.env.example` secrets re-confirm **G1-8**; `DOCKER_GID=0` and
`AI_OFFICE_DOMAIN=localhost` hold.

Whatever `AI_OFFICE_BIND_ADDRESS` opens, it opens the Gateway too — exactly
ADR 0001's stated consequence, still Gateway-Key-protected. The exposure of
the bind address itself is A1/S2's; what is new here is that the Gateway
behind it carries none of the app's depth (I2-1, I2-2, I2-3).

## How this was exercised

Against the real code. The app is built as `startServer` builds it
(`buildApp` with the real `buildGateway`), over a **real listening
socket**: `inject` would skip the server factory, which is exactly where
`gateway-entry.ts` splits `/v1` from the app, so every path case is sent
with `node:http`, which sends raw paths as written. The sandbox directory
is probed by reading `docker-compose.yml` and running the `sandbox-dir`
service's own shell command against a temporary stand-in for `/tmp`, as a
local user who got there first. No production code changed. Probe tests:

- [`apps/server/src/gateway-entry.pen-test.test.ts`](../../../apps/server/src/gateway-entry.pen-test.test.ts):
  the real app and Gateway over a socket; the split (holds), the missing
  headers (I2-1), the body read before refusal (I2-2), the unlimited key
  guessing (I2-3), and redaction (holds).
- [`docker/sandbox-dir.pen-test.test.ts`](../../../docker/sandbox-dir.pen-test.test.ts):
  the `sandbox-dir` service read from compose, its command run against a
  pre-created and a symlinked path (I2-4), the work directory's mode
  (I2-5), and the `.env.example` defaults re-assessed with G1-8.

Each `it.fails` was flipped to `it` once, all together, to see it fails on
its own property assertion and not a setup error: the three in
`gateway-entry` failed with `expected undefined to be 'nosniff'`, `expected
false to be true` (an answer before the body), and `expected [ 401, … ] to
include 429`; the three in `sandbox-dir` with `expected false to be true`
(no symlink guard), `promise resolved … instead of rejecting` (the path is
adopted), and `expected 45 to be +0` (mode `0o055` set). They were then put
back.

## Verdict on every "What to probe" bullet

### One entry point: path confusion between the Gateway and the app

**HOLDS.** `isGatewayPath` is `^\/v1(?:[/?#]|$)`, matched against the raw
request URL before Fastify parses anything. Every confusion case stayed on
the correct side (`gateway-entry.pen-test.test.ts`):

- `//v1/messages`, `/V1/messages`, `/%761/messages` (percent-encoded `v`),
  `/v1%2Fmessages`, `/./v1/messages`, `/api/../v1/messages`,
  `/x/../v1/messages`, and an absolute-form `http://127.0.0.1/v1/messages`
  all fail to reach the Gateway: no AI Provider call, nothing in the
  request log, no `msg_i2` in the body. They are the app's (a 404 or the
  web app), which is the safe direction — a request that does not match
  `/v1` exactly is handled by the app with all its hooks, not slipped to
  the key-only Gateway.
- The reverse — `/v1/../api/session`, `/v1/%2e%2e/api/session`,
  `/v1/..%2Fapi/session`, `/v1/messages/../../api/session`,
  `/v1?/../api/session` — are the Gateway's: each is the Gateway's 404
  ("The AI Gateway has no such route."), never the app's `/api/session`
  (no `csrfToken` in the body), even with the Owner's session cookie
  attached. So `/v1` path traversal cannot reach an app route, and the
  app's hooks never run for a `/v1`-prefixed path.

### `/v1` with a session cookie

**HOLDS.** A `/v1/messages` with only the Owner's session cookie (no
Gateway Key) is `401`: a UI session is not a Gateway credential (as
`gateway-entry.test.ts` already pins). The cookie is in
`droppedRequestHeaders`, so it is never forwarded to the AI Provider; the
probe confirms the upstream sees no `cookie` header and none of the
cookie's value anywhere in its headers.

### CORS / a browser page calling `/v1`

**HOLDS (for the method used).** The Gateway serves only `POST` routes
under `/v1` and a `setNotFoundHandler`; it registers no CORS plugin and no
`OPTIONS` route, so a cross-origin preflight (`OPTIONS /v1/messages` with an
`Origin` and `Access-Control-Request-*`) is a `404` with no
`Access-Control-Allow-Origin` or `-Allow-Headers`. A browser's preflighted
cross-origin POST is therefore refused by the absence of allow-headers. A
*simple* request a browser can send without a preflight still reaches the
Gateway, but cannot carry `x-api-key`/`authorization` as a custom header
and so is refused as keyless (401); DNS rebinding against the host publish
is H19, which G1 found holds. No finding.

### Which app-wide controls no longer apply to `/v1`

**FINDING on security headers (I2-1), body limits (I2-2) and the limiter
(I2-3); logging and redaction HOLD.**

- **Security headers: FINDING (I2-1).** The app's security headers are set
  by an `onRequest` hook (that is how #221 fixes A1-6: "every answer carries
  the security headers … pages, the API, built files, refusals and live
  streams"). But `/v1` is handed to the Gateway's Fastify instance by the
  server factory, *before* the app's Fastify runs any hook, so no app hook
  ever fires for `/v1`. The probe stands a marker `onRequest` hook on the
  app: it runs for `/api/session` and never for `/v1/messages` or
  `/v1/nowhere`, and those answers carry no `x-content-type-options`,
  `referrer-policy`, `x-frame-options`, `content-security-policy` or
  `strict-transport-security`. At this commit the app has no headers either
  (A1-6, #192), so today the two agree; the finding is that **any
  hook-based app-wide fix misses `/v1` structurally**, so a claim that
  "every answer" carries them is false for the Gateway. The Gateway itself
  sets none.
- **Body limits: FINDING (I2-2).** The app refuses a 2 MiB body on
  `/api/login` with `413` (Fastify's default 1 MiB limit). The Gateway's
  own `bodyLimit` is 32 MiB (Anthropic's maximum), and its content-type
  parser buffers the body *before* the handler checks the Gateway Key, so
  an **unauthenticated** `/v1/messages` reads up to 32 MiB before it answers
  `401`. The probe confirms `/v1` consumes a held-back body rather than
  refusing a keyless request first. Exercising this for exhaustion is DoS
  (out of scope); the absence of the control is the finding.
- **The limiter: FINDING (I2-3).** `/api/login` and `/api/login/api-key`
  are rate-limited and record each failure in `sign_in_events` and the
  Activity Feed; twenty guesses at a UI key draw a `429` and failed-sign-in
  events. Twenty guesses at a Gateway Key on `/v1` all answer `401`, draw no
  limit, and record nothing an Owner can see — only a log line, which (good)
  carries neither the key nor the client address. A Gateway Key is the
  prefix plus 32 random bytes, so guessing one is infeasible however many
  guesses are allowed; the finding is the missing depth and the missing
  audit trail, not a feasible key recovery.
- **Logging and redaction: HOLD.** The Gateway logs through a child of the
  app's redacting logger and records each request in `gateway_requests`
  (FR-44), not the request log. A presented Gateway Key, right or wrong,
  appears in no log line — the app's or the Gateway's — and neither does a
  bearer token (`gateway-entry.pen-test.test.ts`). FR-5 holds on `/v1`.

### Gateway Key guessing from the network without a limiter

**FINDING (I2-3), above.** No limiter stands in front of the Gateway Key
check at `/v1`. Infeasible in practice against 256-bit keys, so rated low;
it is the one unauthenticated, unthrottled, unrecorded guess surface the
one entry point adds, reachable from position 1 whenever the bind address
is opened and from position 4 with any lesser stolen credential.

### Whatever `AI_OFFICE_BIND_ADDRESS` opens, it opens the Gateway too

**HOLDS as documented.** The app publishes
`${AI_OFFICE_BIND_ADDRESS:-127.0.0.1}:…:3045`, and 3045 serves `/v1`, so
opening the bind address to the network opens the Gateway — key-protected —
exactly as ADR 0001 states ("whatever that address is opened to, the
Gateway is too, still key-protected") and as the compose and `.env.example`
comments say. Caddy's `tls` profile reverse-proxies every path to
`app:3045`, `/v1` included, with `flush_interval -1` for the Gateway's SSE.
The exposure of the bind address itself, and the setup screen behind it,
are A1/S2's, not re-filed. What this probe adds is that the Gateway behind
that address carries none of the app's depth (I2-1, I2-2, I2-3), and that a
`tls`-profile header default set only in the Caddyfile would reach `/v1`
through Caddy but not the app's own publish.

### Agents under compose: symlink and pre-creation by another local user in `/tmp`

**FINDING (I2-4).** The `sandbox-dir` service runs as `root` and runs
`sh -c 'mkdir -p "$DIR" && chown 1000:1000 "$DIR"'` on
`AI_OFFICE_SANDBOX_DIR` (default `/tmp/ai-office-sandboxes`), before the app
starts, with no `--no-dereference`, no `test -h`, no ownership check, and a
default directly under the world-writable, sticky `/tmp`. Run against a
stand-in `/tmp` as another local user who got there first
(`sandbox-dir.pen-test.test.ts`):

- **Pre-creation:** `mkdir -p` silently adopts a directory the attacker
  already made, keeping the attacker's contents; the following root `chown`
  then hands that attacker-made directory to the app's user (UID 1000).
- **Symlink:** a symlink left at the path is followed — `mkdir -p` on an
  existing symlink-to-directory is a no-op that leaves the symlink, and a
  write "into" the path lands on the attacker's chosen target. On the real
  stack the preceding root `chown` follows the same symlink, so a non-root
  local user gets `root` to `chown` a path of their choosing to UID 1000,
  and controls the directory the app clones Floors into and bind-mounts to
  the app and the host's Docker.

Rated low on the intended deployment (the Owner's own machine or one EC2;
the engagement says the stack is "never a shared host"), where there is no
other local user. **Re-rate to high on any multi-user host**: it is a
root-run, symlink-following `chown` and a confusable clone directory with no
recorded control.

### The clones' permissions on the host

**FINDING (I2-5).** The app creates its work directory with
`mkdir(workDir, { recursive: true })` and no mode (`runner.ts`,
`chat-sessions.ts`), so it takes the process umask (`0022` on a stock host)
→ `0755`. The probe confirms the created directory is group- and
other-readable and -traversable (`mode & 0o055 !== 0`). Beneath it sit every
Floor's clone — the Owner's private repository contents and the read-only
`GH_TOKEN` is *not* written there (it is passed through the environment, a
"Confirm, don't re-test" line that holds), but the source, history and any
Agent-written worktree are. Any local user on the host, or anything sharing
the bind mount, can read them. Same deployment caveat as I2-4: low on a
single-user host, higher on a shared one. Sandboxes themselves mount only
their own run's worktree (S2), not the whole work directory, so this is a
host-side exposure, not a cross-sandbox one.

### What the bind mount at the same path exposes

**Folded into I2-4/I2-5.** The app bind-mounts `AI_OFFICE_SANDBOX_DIR` at
the same path, read-write (no `:ro`), so the app reads and writes the host
directory directly, and the host's Docker mounts each clone from it into the
sandbox by that path. The exposure is the directory's ownership and mode
(I2-4, I2-5): whoever controls or reads the host path controls or reads what
the app and the sandboxes see there. No separate finding.

### `.env.example` set for development, re-assessed with G1-8

**The public secrets re-confirm G1-8 (not re-filed); `DOCKER_GID=0` and
`AI_OFFICE_DOMAIN=localhost` HOLD.**

- **Public secrets: G1-8.** `cp .env.example .env` yields
  `SESSION_SECRET`, `ENCRYPTION_KEY` and `POSTGRES_PASSWORD` that are public
  in the file, and the server only warns. Owned by **G1-8** (#195,
  `apps/server/src/config.pen-test.test.ts`); re-confirmed here, not
  re-filed.
- **`DOCKER_GID=0`: HOLDS.** It adds the app container's process to the
  root group (`group_add: ${DOCKER_GID:-0}`). The app already holds the
  Docker socket, which is root on the host (the S-series), so gid 0 widens
  no trust boundary; on Linux the Owner is told to set the real docker
  group. No finding.
- **`AI_OFFICE_DOMAIN=localhost`: HOLDS.** Compose and `.env.example` both
  default it to `localhost`, so `docker compose --profile tls up` without a
  domain serves `localhost` with Caddy's own local CA — no exposure beyond
  the host, and the comment tells the Owner to set a real domain. No finding.

### `apps/web/vite.config.ts` (the dev proxy)

**HOLDS (read).** In `pnpm dev`, Vite serves the web app on 3045 and
proxies `/api`, `/health` and `/v1/` to the server with
`changeOrigin: false` (keeping the browser's `Host` so the same-site check
passes). The split in development is the server's own, reached through the
proxy, so the `/v1` findings apply identically under `pnpm dev`; the proxy
adds no new surface. No finding.

### Why these severities

- **I2-1, low:** `/v1` serves JSON and SSE to API clients with explicit
  content-types, not HTML a browser renders, so the clickjacking/CSP value
  of the missing headers is small; `nosniff` and `Referrer-Policy` are
  depth. The finding is structural (hooks never run for `/v1`), so a
  remediation of A1-6 or the limiter that assumes "app-wide" covers `/v1`
  would be wrong — re-rate if `/v1` ever returns a browser-rendered body.
- **I2-2, low:** an unauthenticated memory sink bounded at 32 MiB per
  request; exercising it is DoS (out of scope). The control that should
  refuse a keyless request before reading its body is absent.
- **I2-3, low:** the keys are 256-bit random, so the missing limiter does
  not make guessing feasible; it is defence in depth and an audit gap
  (failed Gateway attempts reach no Activity Feed, unlike sign-ins).
- **I2-4, I2-5, low (on the intended deployment):** each needs a local
  account on the host, which the engagement's single-Owner, never-shared
  deployment does not grant, and I2-4 also needs to win a race before the
  first `docker compose up`. There is no recorded control that the host be
  single-user for the `sandbox-dir` step and the clone mode to be safe.
  **Re-rate to high on any multi-user host:** I2-4 is a root-run,
  symlink-following `chown` with a confusable clone directory, and I2-5
  leaks every Floor's private source to other local users.

### What each fix must make true (for the remediation issues; not how)

- **I2-1:** The security headers (and any other app-wide control meant for
  "every answer") reach `/v1` too, whether that answer comes from the app or
  the Gateway — the one entry point carries one set of baseline response
  headers.
- **I2-2:** An unauthenticated `/v1` request is refused before its body is
  read, so a keyless caller cannot make the Gateway buffer a large body.
- **I2-3:** Gateway Key authentication at `/v1` is rate-limited per client
  and a run of failures is recorded where the Owner can see it, as a run of
  failed sign-ins is.
- **I2-4:** The sandbox work directory is created in a way that refuses a
  pre-existing path it does not own and never follows a symlink (a
  symlink-safe, ownership-checked creation), or it lives outside any
  world-writable parent; the root `chown` never follows a symlink.
- **I2-5:** The sandboxes' work directory and the clones beneath it are
  private to the app's user (no group or other access).

## Could not be exercised here, and what would

No Docker, no second host account, no EC2, non-root. On the pen-test stack:

- **I2-4 end to end:** as a second, non-root local user, pre-create or
  symlink `/tmp/ai-office-sandboxes` (to a directory the attacker owns, or
  to a sensitive path), then `docker compose up` and watch the root
  `sandbox-dir` container `chown` the attacker's target to `1000:1000` and
  the app clone Floors into the attacker's directory. (Here the symlink
  follow and the pre-creation adoption were shown against a stand-in `/tmp`;
  the root `chown` following the symlink is read from the command, which
  carries no `--no-dereference`.)
- **I2-5 on the real host:** confirm the work directory's mode on a stock
  Linux host after stand-up, and that a second local user can read a Floor's
  clone beneath it.
- **I2-1, I2-2, I2-3 through Caddy:** confirm the same gaps behind the `tls`
  profile — Caddy forwards `/v1` to `app:3045`, so the app-publish header
  gap is the same, and a Caddyfile header default would reach `/v1` through
  Caddy but not the app's own 3045 publish.
- **The bind address opening `/v1`:** set `AI_OFFICE_BIND_ADDRESS=0.0.0.0`
  and confirm `/v1` answers from another host with a Gateway Key, and
  refuses without one.
