## Verdict in one line

**The session machinery itself holds; what surrounds it does not.** Cookies,
fixation, the fixed 7-day life, sign-out-everywhere, CSRF on every
state-changing route, TOTP replay and recovery codes all hold, and every
route that answers without a session is public by intent. But the limiter
keys on an address any caller that bypasses Caddy chooses (**A1-1, H3
confirmed**); setup is open to whoever reaches it first, including a
DNS-rebinding page (**A1-2, H4 confirmed**); a stolen session mints
credentials that survive sign-out-everywhere and skip TOTP (**A1-3, H5
confirmed and widened**); `409 password_in_use` is an unthrottled oracle
(**A1-4, H5**); changes to the Owner's credentials never reach the Activity
Feed (**A1-5, new**); there are no security headers (**A1-6, H6
confirmed**); lockouts forget on restart and sessions never idle out
(**A1-7, A1-8, H7 confirmed**); and the first Owner password can never be
replaced (**A1-9, new**). Nine findings: three high, four medium, two low.
No critical.

## How this was exercised

Every probe drives the **real Fastify app** (`buildApp`, as `server.ts`
builds it) through `inject`, on an in-memory auth store and event bus and a
clock the probe moves. `inject`'s `remoteAddress` stands for the TCP peer
the app sees, so "a sandbox on `ai-office-sandboxes`" is a peer address in
172.16.0.0/12 and "Caddy" is a trusted first hop. Live streams are read
over a real socket (`listen` on a free port, `fetch`). The Caddyfile is
read as text: running Caddy needs Docker. A restart is a second app on the
same auth store, as a restart on the same Postgres would be. The
route-by-route checks enumerate `server.routeAccess()`, so they cover every
route the app registers, not a hand-picked list. No production code was
changed.

Probe tests (all beside the code they probe), plus one test-only helper,

## Verdict on every "What to probe" bullet

### Setup: open until a password exists; any deployment path where it is reachable before the Owner; anything binding it to the host or a one-time token

**FINDING (A1-2), H4 confirmed.** `POST /api/setup` (`auth/routes.ts:132`)
is open to any caller, from any address, with any `Host`, until a password
exists, and takes nothing but the password the caller chooses. Nothing binds
it to loopback or to a one-time token printed in the logs. The cross-site
check (`isCrossSite`, `auth/sessions.ts:188`) compares `Origin` with `Host`,
and nothing compares `Host` with `PUBLIC_URL`, so a DNS-rebinding page
(`Origin` and `Host` both the attacker's name, resolving to the app) is
judged same-site and its setup accepted
(`setup.pen-test.test.ts`, "A1-2"). What holds: a 404 for good once a
password exists, across a restart; only one of six concurrent setups wins;
a cross-site `Origin`/`Sec-Fetch-Site`, `Origin: null`, a form body (415)
and a `text/plain` body (400) are all refused; Argon2id with OWASP's
parameters.

Deployment paths in which the app is reachable before the Owner:

| Path | Reachable before setup by | Evidence |
|---|---|---|
| `docker compose up` (default) | Any process or local account on the host, and a DNS-rebinding page in the Owner's browser: the app is published on `127.0.0.1:3045` | `docker-compose.yml`; rebinding pinned by the probe |
| `AI_OFFICE_BIND_ADDRESS=0.0.0.0` (offered by `.env.example`) | The whole network | `docker-compose.yml` `ports` |
| `--profile tls` on a laptop | The network: Caddy's `80:80` and `443:443` publish on every interface, and with the default `AI_OFFICE_DOMAIN=localhost` a caller only needs to send SNI and `Host: localhost` | `docker-compose.yml` `caddy.ports` |
| `pnpm dev` / `pnpm start` outside compose | The network: `HOST` defaults to `0.0.0.0` (unlike `GATEWAY_HOST` and `OAUTH_CALLBACK_HOST`) | `setup.pen-test.test.ts` pin; `config.ts:93` |
| EC2 per `deploying-to-ec2.md` | Only the Owner, **if** the security group or Tailscale is in place first; §7 says so ("whoever reaches the setup screen first sets it") | Read; the control is the document |
| A sandbox (position 3) | Not before setup: no Floor, so no Agent, exists until the Owner has signed in | Read |

### Login: Argon2id; the limiter keyed on the client address; `X-Forwarded-For` rotation with `TRUST_PROXY=1` from a direct caller; the suggested CIDR

- **Argon2id — HOLDS.** `$argon2id$v=19$m=19456,t=2,p=1$` (OWASP's), a
  fresh salt each time; any string is checked at sign-in.
- **The limiter keyed on the client address — HOLDS when the address is
  real.** Five free failures, then a doubling lockout; concurrent guesses
  cannot slip past (each counts before the hash is checked); a right
  password awaiting TOTP is withdrawn, not counted as success; IPv6 keyed by
  /64. With `TRUST_PROXY` unset, `X-Forwarded-For` is ignored, even from a
  sandbox's address. With `TRUST_PROXY=1`, a forged entry *before* the
  nearest hop is not used.
- **`X-Forwarded-For` rotation with `TRUST_PROXY=1` from a direct caller —
  FINDING (A1-1), H3 confirmed.** `trustHops(1)` (`app.ts:400`) trusts the
  nearest hop whoever it is, so a caller that reaches the app's port
  directly sets a single `X-Forwarded-For` and is limited by that. Twenty
  wrong passwords from one sandbox address, each claiming a new address:
  twenty `401`s, no `429`, and the right password still signs in at once.
  The same rotation guesses TOTP codes at `/api/login/totp` (a wrong code
  does not end the challenge) and keys at `/api/login/api-key` without
  limit, and every forged address is what `sign_in_events` and the Activity
  Feed record.
- **The suggested CIDR — FINDING (A1-1).** `.env.example`'s
  `172.16.0.0/12` covers Docker's default bridge pools, and so the
  `ai-office-sandboxes` network. A peer there is trusted as a proxy: the
  same twenty guesses, the same result.
- **Through Caddy — HOLDS (read, not run).** Caddy's `reverse_proxy` ignores
  a client's `X-Forwarded-*` unless the client is in `trusted_proxies`,
  which the Caddyfile does not set (Caddy documentation, pinned in
  `caddyfile.pen-test.test.ts`). The gap is every caller that does not come
  through Caddy. Whether a sandbox can reach `app:3045` at all is #193; from
  the compose file it can (the app joins `ai-office-sandboxes` and listens
  on `0.0.0.0`).

### Repeated failures recorded in the Activity Feed

**HOLDS for sign-ins.** Each failed password, code and Gateway Key sign-in
publishes `sign_in.failed` (address, user agent, second factor), the one
that starts a lockout publishes `sign_in.locked_out`, and none carries the
password or key (`login-limiter.pen-test.test.ts`). Two gaps: the address
recorded is the forged one under A1-1; and wrong codes to turn TOTP off,
the oracle's guesses (A1-4) and every change to the Owner's credentials are
recorded nowhere the Owner looks (**A1-5**).

### `POST /api/owner-passwords`: re-auth and TOTP required or not; `409 password_in_use` as an oracle; rate limit

- **Re-auth and TOTP — FINDING (A1-3), H5 confirmed and widened.** Neither
  is asked for (`password-routes.ts:75`). A stolen session adds a password;
  the Owner signs out everywhere; the attacker signs straight back in with
  it. The hypothesis missed two worse routes from the same session: with
  TOTP on, it makes a Gateway Key with UI access (`POST /api/gateway-keys`),
  which after sign-out-everywhere signs in **with no TOTP code**; and with
  TOTP off, it turns TOTP on with the attacker's own secret and keeps the
  ten recovery codes, after which the Owner's password alone no longer
  signs in.
- **`409 password_in_use` as an oracle — FINDING (A1-4).** Ten
  policy-conforming misses are each answered `201`; the Owner's own password
  is answered `409 password_in_use`. Each miss also adds a working Owner
  password, which the attacker deletes again.
- **Rate limit — none (A1-4).** No `429`, no `sign_in_events` row, no
  Activity Feed event, for any number of guesses. Each costs the server one
  Argon2id hash per existing password and one to store (volume is out of
  scope; the absence is the finding).

### TOTP: enrolment, recovery codes, replay of a code, API-key sessions that skip it

- **Enrolment — HOLDS**, apart from who may do it (A1-3). The secret is
  shown once, `no-store`, sealed (`aio1:`) until a code confirms it; a wrong
  confirming code and a second enrolment while on are refused. The
  challenge cookie is `HttpOnly; SameSite=Strict; Path=/api/login;
  Max-Age=300`, and a right password starts no session.
- **Recovery codes — HOLD.** Ten distinct 80-bit codes; only SHA-256 hashes
  kept; each works once, case- and dash-insensitively; guesses count
  against the limiter.
- **Replay of a code — HOLDS.** The code that confirmed enrolment, a code
  already used to sign in and an older code are refused (each time step is
  used at most once, `useTotpTimeStep`); of two sign-ins racing with one
  code, one wins. In memory this is one call; in Postgres it is one
  `UPDATE … WHERE last < step`, which was read, not run (no Postgres here).
- **API-key sessions that skip it — by design** (`routes.ts:205` says so: the
  key is a long random secret). It becomes a finding only with A1-3: a
  session, including one that skipped TOTP, can mint such a key.
- **Turning TOTP off — HOLDS:** it needs a current code, and wrong codes
  count against the limiter. A stolen session cannot do it.

### Sessions: cookie flags, fixed 7-day life, idle timeout, sign-out-everywhere revokes API-key sessions too, fixation, CSRF on every state-changing route

- **Cookie flags — HOLD.** `ai_office_session=<256-bit token>; Path=/;
  Max-Age=604800; HttpOnly; SameSite=Strict`, plus `Secure` when
  `PUBLIC_URL` is https. Only the token's SHA-256 is stored. (No `__Host-`
  prefix: hardening only, not a finding.)
- **Fixed 7-day life — HOLDS.** Used every day for six days, refused on the
  seventh; use never extends it; an expired session is refused by every
  guarded route.
- **Idle timeout — FINDING (A1-8), H7 confirmed.** None: a cookie unused
  for 6 days 23 hours still works. FR-2 promises no idle timeout, so this is
  depth, not a broken promise.
- **Sign-out-everywhere revokes API-key sessions too — HOLDS.** It deletes
  every session, password- and key-begun alike, and an open live stream
  held by a Gateway Key session (`/api/events/stream`,
  `/api/terminal/stream`, `/api/gateway/requests/stream`,
  `/api/gateway/logs/stream`) closes at its next heartbeat. The Manager
  chat's and direct chats' streams use the same `signedIn` heartbeat
  (`app.ts`), read but not run (they need a Floor). Revoking a key, or
  removing an Owner password, ends that credential's sessions at once. It
  does **not** revoke the credentials themselves: see A1-3.
- **Fixation — HOLDS.** A cookie value the attacker planted before sign-in
  is never adopted; signing in over a live session issues a new token.
- **CSRF on every state-changing route — HOLDS.** Every `owner` route with
  a state-changing method (more than 100, enumerated from the app) refuses
  a signed-in request without `x-csrf-token` with `403`, and refuses one
  from another site even *with* the token (`403 csrf_refused`); one
  session's token does not work for another; the three sign-in routes
  refuse another site (login CSRF). No route sends
  `Access-Control-Allow-Origin`. The Manager chat's attachment upload (#204)
  needs the token, and takes no `multipart/form-data` (415) or `text/plain`
  (400) body, so a cross-site form cannot post one.

### Limiter and challenge state survive a restart or not

- **Limiter — FINDING (A1-7), H7 confirmed.** In memory
  (`login-limiter.ts:73`). A client locked out before a restart gets five
  fresh guesses after it, though `sign_in_events` still holds its
  failures.
- **Sign-in challenges — HOLD (fail closed).** In memory
  (`sign-in-challenges.ts:38`); after a restart a pending challenge is
  `401 sign_in_expired`, and the Owner types the password again.

### Security headers on the app and through Caddy

**FINDING (A1-6), H6 confirmed.** The login page, a signed-in page, `GET
/api/session` and a built file carry none of CSP, `X-Frame-Options`,
`X-Content-Type-Options`, `Referrer-Policy` or HSTS, even with an https
`PUBLIC_URL`; the Caddyfile has no `header` directive. The only exceptions
are the Manager chat's attachment downloads (their own CSP, `nosniff`,
`sandbox`) and the OAuth callback page (H14, not this listener).
`SameSite=Strict` keeps a framed Office signed out, which blunts
clickjacking, but nothing stops a first plain-http visit being
downgraded, or the login page being framed.

### Prove the negative: every route, live stream and WebSocket

**HOLDS.** Enumerated from the app, not from a list:

| Answers without a session | Access | In FR-2? | Public by intent because |
|---|---|---|---|
| `POST /api/setup` | setup | yes | The setup screen; a 404 once a password exists (but see A1-2) |
| `POST /api/login` | sign-in | yes | The login page's API |
| `POST /api/login/totp` | sign-in | no | Its second step; needs the challenge cookie a right password starts |
| `POST /api/login/api-key` | sign-in | no | Sign-in with a Gateway Key with UI access |
| `GET`/`HEAD /health` | public | yes | Compose's health check (FR-47); says `ok`/`up` and nothing else |
| `POST /api/github/webhooks` | public | no | GitHub's deliveries, believed only when HMAC-signed (the W series) |
| `GET`/`HEAD /robots.txt`, `/sitemap.xml` | public | no | For crawlers; name only `/login` |
| The built web app's files | public | no | The login page needs them; they hold no data; no listing, no traversal |
| Pages | — | `/login`, `/setup` | Every other page redirects to `/login`; `/setup` is a 404 after setup |

Every other route — 180-odd — answers `401` with no session and with an
expired one, and an unknown `/api/` path answers `401` too, so paths cannot
be enumerated. The **live streams** are exactly six, all `owner`:
`/api/events/stream`, `/api/floors/:floorId/manager-chat/stream`,
`/api/floors/:floorId/agents/:agentId/chat/stream`, `/api/terminal/stream`,
`/api/gateway/requests/stream` and `/api/gateway/logs/stream`. There is **no
WebSocket**: the HTTP server has no `upgrade` listener, and an upgrade
request is answered as plain HTTP (`401`).

Decisions to record, not findings:

- **FR-2's list is out of date.** Five of the open routes and the built
  files are beyond FR-2's three. Each is intended; the drift is H17's, owned
  by the I series.
- **The version check is not public.** `GET /api/version/latest` (#204) is
  `owner`; without a session it is `401` and GitHub is not asked.
- **The #204 routes are all `owner`**: the Manager chat's attachment
  upload and download, file mentions and task list, and the changed Agent,
  AI Provider and analytics routes (all in the enumeration above).
- **`robots.txt` allows crawling `/`** and the sitemap names `/login`, so
  an exposed Office invites indexing of its login page. With `PUBLIC_URL`
  unset, both (and `index.html`) use the request's `Host`, escaped.
- **Other listeners** are not this app: the AI Gateway (3047, Gateway Keys,
  #195 and H19) and the OAuth callback (1455, H14, #193).

### Why these severities

- **A1-1 high:** the limiter (FR-4) holds only in the network layer —
  only while every caller comes through Caddy. From position 3 it is gone,
  and with it the bound on TOTP guessing. Not critical: the attacker still
  has to guess a password the policy makes long.
- **A1-2 high:** the network is the whole of setup's authorisation. Not
  critical by default (loopback), but several documented paths widen it,
  and a rebinding page needs no network position at all, only the Owner's
  browser before the Owner sets the password.
- **A1-3 high, above H5's medium:** sign-out-everywhere (FR-2) and TOTP
  (FR-3) are the two controls the Owner has to recover from a stolen
  session; one request from that session defeats both, permanently.
- **A1-4, A1-5, A1-9 medium:** each is a control weaker than the
  documents claim — FR-4 (sign-in guesses are limited and recorded), FR-52
  (configuration changes are in the Activity Feed; `config.changed` even
  has an unused `security` scope) and FR-65 ("Password" in the office
  admin).
- **A1-6 medium:** defence in depth; `SameSite=Strict` and React's escaping
  carry the load today.
- **A1-7, A1-8 low:** the lockout is at most an hour and needs a restart to
  lose; FR-2 promises no idle timeout. Hygiene.

### What each fix must make true (for the remediation issues; not how)

- **A1-1:** The address a sign-in is limited by is one the caller cannot
  choose: `X-Forwarded-For` is believed only from the proxy that is really
  in front of AI Office, never from a sandbox or any other direct caller,
  whatever `TRUST_PROXY` the documents suggest.
- **A1-2:** The first password can be set only by someone who holds
  something from the host (such as a one-time token AI Office prints, or a
  request from loopback), and a request for a name AI Office is not served at
  is refused.
- **A1-3:** Adding an Owner password, making or widening a Gateway Key with
  UI access, and turning TOTP on need a fresh proof of the Owner (the
  current password, and the TOTP code when on), which a session begun with
  a Gateway Key cannot give; and sign-out-everywhere tells the Owner which
  credentials still sign in.
- **A1-4:** A session cannot learn whether a candidate is an Owner password
  faster than the sign-in limiter allows, and each such check is recorded
  as a sign-in attempt is.
- **A1-5:** Every change to how the Owner signs in (passwords added or
  removed, TOTP on or off, refused attempts to turn it off) is in the
  Activity Feed, without the secret.
- **A1-6:** Every page and API answer, from the app and through Caddy,
  carries a CSP with `frame-ancestors` (or `X-Frame-Options`),
  `X-Content-Type-Options: nosniff` and a `Referrer-Policy`, and HSTS
  whenever it is served over https.
- **A1-7:** A lockout outlives a restart of the process.
- **A1-8:** A session left unused for an idle period the Owner can see (and
  the PRD states) is refused.
- **A1-9:** The Owner can replace the first password, with proof of the
  current one, and doing so ends the sessions it began.

## Could not be exercised here, and what would

- **Caddy itself** (its handling of `X-Forwarded-For` and `Host`, and the
  headers it sends) needs Docker. The Caddyfile is pinned as text, and
  Caddy's behaviour is from its documentation. On the live stack: `curl -H
  'X-Forwarded-For: 1.2.3.4' https://<domain>/api/login` six times with a
  wrong password must reach `429`; `curl -I https://<domain>/login` shows
