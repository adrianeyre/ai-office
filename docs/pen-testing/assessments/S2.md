## Verdict in one line

**H2 is CONFIRMED and H3's reach is CONFIRMED; H14's listener HOLDS.** A
sandbox has a route to anywhere (S2-1) and, on the EC2 set-up as
documented, to the instance's role credentials (S2-2). Besides the
Gateway it reaches the app's web app, API and sign-in routes and the OAuth
callback (S2-3). It starts with nothing beyond Docker's defaults (S2-4)
and shares one bridge with every other Floor's sandboxes (S2-5). What holds:
the sign-in callback cannot be cancelled, failed or raced without the
Owner's state. The environment allow-list, the AI Account credential
refusal and the read-only `GH_TOKEN` hold too. No sandbox is privileged,
holds the Docker socket or runs as root, and each mounts only its own
clone.

## How this was exercised

- **Run flags and mounts.** The real `dockerSandbox` (Sandcastle's Docker
  provider, wrapped in `allowListed` as the runner wraps it) and the real
  `dockerToolRunner` were driven against a stand-in `docker` CLI first on
  the `PATH`. It records the exact arguments and answers `image inspect`,
  `ps` and `run`. What it recorded is the `docker run` the live stack
  issues. The mounts given to the provider are those Sandcastle's `branch`
  strategy builds (`startBindMountSandbox`, `resolveGitMounts` in
  `@ai-hero/sandcastle/dist/chunk-VOG34SRF.js`).
- **Network and reach.** `docker-compose.yml`, `docker-compose.dev.yml`
  and `docs/processes/deploying-to-ec2.md` were read, and the real
  `loadConfig` was driven with compose's own `app.environment`, to get the
  addresses the server, the Gateway and the callback listener bind.
- **The OAuth callback.** The real `createOAuthCallbacks`, bound `0.0.0.0`
  as compose binds it, was put in front of the real `createAiAccounts` and
  the fake OpenAI-shaped OAuth server (PKCE checked). The "sandbox" sent its
  requests from this machine's non-loopback address (`eth0`), as a peer
  on a bridge arrives.
- **Environment.** `sandboxEnvironment`, `allowedEnvironment`,
  `refuseAiAccountCredentials` and `agentToolSetup` were driven with hostile
  keys and values. The read-only token came from the real
  `createGitHubApp` against the fake GitHub, which grants each call only the
  permission GitHub asks of it.

No production code was changed. Probe tests:
- `packages/orchestrator/src/sandbox/docker-run.pen-test.test.ts`
- `docker/sandbox-isolation.pen-test.test.ts`
- `apps/server/src/ai-accounts/oauth-callback.pen-test.test.ts`
- `packages/orchestrator/src/sandbox/environment.pen-test.test.ts`

### Two deployment shapes

The app image has neither `git` nor the `docker` CLI
(`docs/guide/issue-pipeline.md`, "Progress comments";
`deploying-to-ec2.md`, "Agents under compose"). So **today Agents work only
when the server runs outside compose** (`pnpm dev`, `pnpm start`). Its
sandboxes then join Docker's default bridge unless `SANDBOX_NETWORK` names
another, and they reach the host at the bridge's address. The compose stack
is the shape the documents prescribe for EC2, and it applies as soon as the
image gains those tools. Every verdict below says which shape it is for.

## Verdict on every "What to probe" bullet

### Egress: arbitrary hosts; `169.254.169.254`; the IMDSv2 hop limit in the documented EC2 set-up

- **Arbitrary hosts: FINDING (S2-1), H2 confirmed.** `ai-office-sandboxes`
  is an ordinary bridge network, not `internal: true`. Nothing in the tree
  filters a sandbox's egress or makes it use a proxy: no key a sandbox is
  given names one, and neither compose file mentions egress, `iptables` or
  the metadata address. Outside compose, Docker's default bridge has a
  route out too. So an injected Agent can send the clone, its read-only
  `GH_TOKEN` (one hour, this repository) and its Gateway Key anywhere.
  Pinned in `sandbox-isolation.pen-test.test.ts`, "S2-1".
- **`169.254.169.254` and the hop limit: FINDING (S2-2), H2 confirmed.**
  The EC2 process picks **Ubuntu Server 24.04 LTS** and **Metadata version:
  V2 only**. It never sets the hop limit, and it suggests an **IAM role**
  on the instance for S3 backups. Ubuntu 24.04 AMIs are registered with
  `ImdsSupport: v2.0`, and for such an AMI AWS defaults
  `HttpPutResponseHopLimit` to **2** unless the launch or the account says
  otherwise. Two hops is enough for a container on a Docker bridge to get an
  IMDSv2 token and read the role's temporary credentials. These AWS defaults
  come from AWS's documentation (`configuring-IMDS-new-instances`,
  `API_Image`) and Canonical's LP #2075385; they were not run here. The doc
  is pinned in "S2-2".
- **What holds:** IMDSv1 is off on the documented set-up ("V2 only"), so a
  metadata request without a token is refused.

### Reach into the stack: `app:3045`, `app:1455`, `app:3047`, Postgres, Caddy, other sandboxes

- **`app:3045` and `app:1455`: FINDING (S2-3), H3 reach confirmed, H14
  reach confirmed.** Under compose the app joins `ai-office-sandboxes` and
  `loadConfig` binds `HOST=0.0.0.0` (3045: the web app, the API, `/api/login`,
  `/api/setup`, the webhook route), `OAUTH_CALLBACK_HOST=0.0.0.0` (1455,
  while a sign-in waits) and `GATEWAY_HOST=0.0.0.0` (3047). Docker
  publishes 1455 and 3047 to the host's loopback, but that only limits the
  host side. On the sandboxes' network every one of them answers. The
  compose file says sandboxes reach "the AI Gateway as app:3047 and nothing
  else of the stack", which is wrong (H17). Outside compose, `HOST`
  defaults to `0.0.0.0`, so a sandbox on the default bridge reaches the
  server at the bridge's address (172.17.0.1 on Linux) as well as the
  Gateway. This reach is what makes A1-1 (limiter bypass by
  `X-Forwarded-For`) usable from position 3. Pinned in
  `sandbox-isolation.pen-test.test.ts`, "S2-3", and by the callback test
  "answers a peer on a non-loopback address".
- **`app:3047`: intended.** The Gateway is meant to be reached
  (ADR 0001). What a Gateway Key can do there is #195.
- **Postgres: HOLDS.** Under compose, Postgres is on `default` only and
  publishes no port. In development it is published on `127.0.0.1:3048`
  only, which Docker does not forward from a bridge.
- **Caddy: HOLDS.** It is on `default` only.
- **Other sandboxes: FINDING (S2-5).** Every sandbox, of every Floor, joins
  the one `ai-office-sandboxes` network (or the one default bridge), and
  inter-container traffic is on (no `enable_icc` option, no per-sandbox
  network). So one sandbox reaches any port another listens on, such as a
  Floor's dev server or test database started by its setup command.
  Turning inter-container traffic off on that network would also cut
  sandboxes off from `app:3047`, so the fix needs a decision (a network per
  sandbox, or the Gateway reached another way).

### The OAuth callback listener: can a sandbox cancel, fail or race the Owner's ChatGPT sign-in?

**HOLDS on all three** (`oauth-callback.pen-test.test.ts`). The reach is
S2-3.

- **Cancel:** a callback with `?error=` is answered 400 without touching
  the sign-in. It is still awaited, and the Owner's own landing then adds
  the account.
- **Fail:** callbacks with no state, an empty state, a guessed state or a
  43-character made-up state are each answered "expired or is unknown".
  `completeCallback` finds no sign-in, so nothing is deleted. A sign-in is
  only ever dropped (`refused`) after its state has matched. The Owner's
  sign-in still finishes.
- **Race:** the state is 32 random bytes (256 bits), new for each sign-in
  and shown only in the Owner's browser. PKCE is S256, so a code for any
  other sign-in cannot be exchanged. Once the Owner's callback finishes,
  the sign-in is gone and the listener stops, and a later callback adds
  nothing.
- The 400 page escapes what it shows and names no secret.

### Run flags: capabilities, `no-new-privileges`, user, memory and PID limits, read-only root, seccomp/AppArmor, devices

Both ways AI Office starts a container were probed: Sandcastle's
`docker run -d` for task and fact-finding sandboxes, and `dockerToolRunner`'s
`docker run --rm -i` for Manager chat sessions and subscription model calls
(`docker-run.pen-test.test.ts`).

| Flag | Verdict |
|---|---|
| Capabilities | **FINDING (S2-4).** No `--cap-drop`: Docker's default set, including `NET_RAW`. It is not effective for a non-root user, but it is in the bounding set and binaries with file capabilities (such as `ping`) use it |
| `no-new-privileges` | **FINDING (S2-4).** Not set: a setuid binary in the image can still raise privileges |
| User | **HOLDS.** Sandcastle passes `--user <uid>:<gid>` of the AI Office process, never root, and the images set `USER` to the same `agent` user (`dockerToolRunner` relies on that). There is no `sudo` in the images |
| Memory and PID limits | **FINDING (S2-4).** Neither `--memory` nor `--pids-limit` is set: one sandbox can take the host's memory or process table from the app, Postgres and every other sandbox (absence only; not exercised, as DoS is out of scope) |
| Read-only root | **FINDING (S2-4).** No `--read-only`: the image's filesystem is writable for the sandbox's life |
| Seccomp, AppArmor | **HOLDS.** No `--security-opt` at all, so Docker's default profiles apply |
| Devices, privileged, host namespaces | **HOLDS.** No `--device`, `--privileged`, `--cap-add`, or host `--pid`/`--ipc`/`--uts`/`--userns`/`--cgroupns`/`--network` |

### Mounts: what is mounted read-write, whose files, what a sandbox can read of another Floor's work directory

**HOLDS** (`docker-run.pen-test.test.ts`, "who a task's sandbox runs as,
and what it mounts").

- **A task's sandbox:** read-write, its own clone's worktree (at
  `/home/agent/workspace`), the worktree's `.git` file and the clone's
  `.git` directory, at their host paths. Read-only, its Skills and memory.
  The clone is `<SANDBOX_WORK_DIR>/runs/sbx-<uuid>`, one per run. Nothing of
  another run, Floor or the work directory's root is mounted. The
  read-write `.git` is how S1 (H1) planted code for the host side, and
  #201/#203 fixed that.
- **A Manager chat session:** its Floor's clone **read-only**, and its tool's
  state (`<workDir>/manager-chat/<floor>/claude|codex`) **read-write**, which
  persists across turns and restarts by design. Whether a session can write
  there with its read-only tools is H18 (P2), not this probe.
- **Whose files:** the sandbox writes as AI Office's own uid and gid, so its
  files belong to the user that runs AI Office. Outside compose, that is the
  Owner's own login on the host. Supplementary groups, such as `docker`, are
  not carried in.
- **The Docker socket** is never mounted into a sandbox.

### Environment: the allow-list, the AI-Account-credential refusal and the read-only `GH_TOKEN`

**HOLDS** (PRD "Confirm, don't re-test"; `environment.pen-test.test.ts`
and `docker-run.pen-test.test.ts`).

- **The allow-list** is exactly the Git identity, `GH_TOKEN` and each agent
  tool's way to the Gateway. It matches key names exactly, with no case or
  whitespace variants. It drops everything else Sandcastle gathers, such as
  keys a repository's `.sandcastle/.env` names from the app's environment
  (`DATABASE_URL`, `SESSION_SECRET`, `ENCRYPTION_KEY`,
  `GITHUB_APP_PRIVATE_KEY`, `DOCKER_HOST`, `NODE_OPTIONS`, `LD_PRELOAD`,
  proxies). The recorded `docker run` carries only those keys plus `HOME`.
  `dockerToolRunner` passes `-e NAME` only for allow-listed names.
- **The refusal:** a value shaped like an Anthropic, OpenAI, xAI or Google
  key, or a JWT, is refused under any key, even inside a longer value. One
  of the Owner's stored credentials is refused whatever its shape. Every
  agent tool takes only a Gateway Key, and a key carrying a newline (which
  could add a header) is refused.
- **`GH_TOKEN`** is minted for the Floor's repository alone, with `contents`,
  `issues`, `pull_requests` and `checks` at `read`. With it, a sandbox reads
  the issue but cannot comment, open an issue or pull request, or push a
  ref (403 each), and cannot read another repository in the same
  installation.

### Why these severities

- **S2-1 high:** egress is the step after every position-2 success. The
  only control is that the sandbox holds nothing that can write, and that is
  one layer. The read-only token still reads a private repository, and the
  Gateway Key still spends the Owner's AI Accounts until it is revoked.
- **S2-2 high:** a sandbox crosses into the instance's AWS identity. With
  the documented backup role, that means the backup bucket. It is not rated
  critical because it is not the host, an AI Account or the App key, but
  the role's policy decides how far it goes. Re-rate if the role is wider.
- **S2-3 high:** the boundary the compose file claims (Gateway only) does
  not exist. It is what turns A1-1 and A1-2 into position-3 attacks. Rated
  against the compose stack; outside compose the host's other listeners on
  `0.0.0.0` are in reach too.
- **S2-4, S2-5 medium:** undefended in depth. The non-root user and Docker's
  default seccomp and AppArmor profiles do hold, and nothing here turns
  either into an escape by itself.

### What each fix must make true (for the remediation issues; not how)

- **S2-1:** A sandbox reaches only what its work needs: the AI Gateway,
  plus whatever the Owner explicitly allows (such as a package registry or
  GitHub), and nothing else on the internet or the local network.
- **S2-2:** On the EC2 set-up AI Office documents, no sandbox can reach the
  instance metadata service, whatever hop limit the AMI or the account
  defaults to.
- **S2-3:** From a sandbox, the app answers only as the AI Gateway: nothing
  on its web app and API port, its OAuth callback port or any other
  listener of the host or the stack. The compose file's comment says what
  is true.
- **S2-4:** Every container AI Office starts for an Agent drops the
  capabilities it does not need and cannot gain privileges. It has bounded
  memory and processes, and writes only where it works. This holds for both
  the Sandcastle sandboxes and `dockerToolRunner`.
- **S2-5:** A sandbox cannot reach another sandbox, of its own Floor or
  another's, while each still reaches the AI Gateway.

## Could not be exercised here, and what would

There is no Docker and no EC2 in this sandbox. On the pen-test stack,
position 3's harness (PRD "How the red team is wired") would confirm each
finding from inside a real sandbox, on the network, mounts and environment
an Agent gets:

- **S2-1:** an HTTPS request from the sandbox to a host the red team
  controls succeeds.
- **S2-2:** on an instance launched as the EC2 process says,
  `aws ec2 describe-instances` shows `HttpPutResponseHopLimit: 2`. From a
  sandbox, an IMDSv2 token request to `169.254.169.254` is answered. The
  harness stops there and does not read the role.
- **S2-3:** from a sandbox, `http://app:3045/health` and, while the Owner's
  test sign-in waits, `http://app:1455/auth/callback` answer. Outside
  compose, `http://172.17.0.1:<PORT>/health` does.
- **S2-4:** `docker inspect` of a running sandbox shows an empty
  `HostConfig.CapDrop`, an empty `SecurityOpt`, `Memory: 0`,
  `PidsLimit: null` and `ReadonlyRootfs: false`.
- **S2-5:** a listener started in one sandbox is reachable from another.
- **Postgres and Caddy holding** was read from the compose files and Docker's
  documented behaviour for loopback-published ports. On the stack, a
  connection from a sandbox to `postgres:3048` should fail to resolve, and
  one to the host's `127.0.0.1:3048` should be impossible from a container.

## Out of scope here

- Host-side git in Agent-written worktrees: S1 (#186), fixed by #201 and
  #203.
- What a sandbox's Gateway Key can do at the Gateway: #195.
- Login brute force through the client address: A1-1 (#192). S2-3 is the
  reach it depends on.
