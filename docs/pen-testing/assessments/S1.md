## Verdict in one line

**H1 is CONFIRMED (2026-10-11).** From a worktree whose `.git` an Agent has
written (position 3), AI Office's own host-side git calls, and Sandcastle's,
execute code the Agent planted — in the app container that holds the Docker
socket, the GitHub App key (ADR 0002) and every AI Account. Two findings,
both claimed **critical**. The control the PRD register hoped for — that
`runGit` neutralises the repository's own config, or that the worktree is
never git'd in the app container — does not exist.

## How this was exercised

Every host-side git call AI Office makes funnels through `runGit`
(`packages/orchestrator/src/git/command.ts`). The probe drives the **real
`runGit`** with the **real argument vectors** the call sites use, against a
real git repository in a temp dir whose config and hooks stand in for what
an Agent would plant. A marker file written by the planted code is proof the
app process ran it. Sandcastle's own runner is an installed dependency
(`@ai-hero/sandcastle`); its git wrapper `execGit` was read from
`dist/chunk-VOG34SRF.js` and pinned by driving git with its exact
environment and subcommands. No production code was changed.

Probe tests:
- `packages/orchestrator/src/git/command.pen-test.test.ts`
- `packages/orchestrator/src/git/publish.pen-test.test.ts`
- `packages/orchestrator/src/sandbox/sandcastle-git.pen-test.test.ts`

## The host-side call sites, and the config each trusts

`runGit` sets `GIT_CONFIG_NOSYSTEM=1` and `GIT_CONFIG_GLOBAL=/dev/null`, so
it neutralises **system and global** config. It sets **no** override for the
repository's own `.git/config`, `.git/hooks`, `core.hooksPath`,
`core.fsmonitor` or filters. So every call below trusts, and runs, whatever
the Agent wrote into the repo it runs in:

| Call site | Command(s) on the Agent-written repo | Exec reached |
|---|---|---|
| `saveUncommitted` (`sandbox/runner.ts:382`), Fresh Start | `git status --porcelain`; `git add --all`; `git commit --quiet --no-verify` | `core.fsmonitor`; `filter.*.clean`; `post-commit`, `reference-transaction` |
| `fact-finding.ts:~241` (Grilling, read-only) | `git rev-parse HEAD`; `git status --porcelain` | `core.fsmonitor` |
| `changedFiles` (`coder/coder.ts:168`) | `git show --no-renames --name-only --format=` | none today (`--name-only`, no patch) |
| Fresh Start summary (`runner.ts`) | `git diff --name-only …`; `git log --format=%s …` | none today (`--name-only`) |
| `branchCommits` (`runner.ts`) | `git rev-list …` | none |
| `publishBranch` (`git/publish.ts`) | fetches the branch into a **fresh bare repo** with `core.hooksPath=/dev/null`; commits/rebases there | none (see below) |
| Sandcastle `execGit` (worktree mgmt, merge-back) | `git worktree add …`; `git merge …`; `git fetch …` | `post-checkout`; `post-merge`/`post-commit`; **no config neutralised at all** |

### Each host-side call site: which config does it trust, and with what flags?

Answered in the table above. In short: every `runGit` call trusts the
repository's own `.git/config`, `.git/hooks` and `.gitattributes` in full;
it neutralises only system and global config. Sandcastle's `execGit` trusts
those **and** system/global config, passing the whole process environment
unchanged with only `LC_ALL=C` added.

### Does `--no-verify` stop any of it?

**It stops only the two hooks it is defined to stop — `pre-commit` and
`commit-msg` — and nothing else.** It does not stop `post-commit`,
`reference-transaction`, `core.fsmonitor` or filters. Confirmed both ways:
`command.pen-test.test.ts` pins that `--no-verify` *does* skip `pre-commit`
(the control that holds) while `post-commit` and `reference-transaction`
still run. So `--no-verify` is not a defence against H1; it is a defence
against a different thing (the Agent's own `commit-msg` policy).

### Sandcastle's own host-side git calls — exposed the same way?

**Yes, and worse (S1-2).** AI Office runs Agents with Sandcastle's `branch`
strategy, whose worktrees live under `.sandcastle/worktrees/<branch>` in the
host clone and are reused across sessions. Sandcastle manages them with
`execGit`, which spawns git with `{ ...process.env, LC_ALL: "C" }` — it does
not set `GIT_CONFIG_NOSYSTEM`/`GIT_CONFIG_GLOBAL` and sets no
`core.hooksPath`. `git worktree add` runs `post-checkout`; `git merge` (the
fast-forward of a reused worktree to origin) runs `post-merge`. Both were
pinned. This path is reached on the **second** session for an issue whose
worktree a prior session wrote (a Fresh Start, or any resumed task), so it
needs no new entry point beyond H1's own.

### What the app container would hand over if the planted code ran

From `docker-compose.yml` and `.env`, the process that runs the planted code
is the **app** container, and it holds, in its environment or on its mounts:

- **The host's Docker socket** — `/var/run/docker.sock` bind-mounted, with
  `group_add: ${DOCKER_GID}` (`docker-compose.yml:84`). Write access to the
  socket is root-equivalent on the host: the planted code can
  `docker run -v /:/host …` and read or write anything on the host.
- **`GITHUB_APP_PRIVATE_KEY`** (`docker-compose.yml:64`) — ADR 0002's App
  key: write to every installed repository, author commits as the Owner,
  and merge.
- **`ENCRYPTION_KEY`** and **`SESSION_SECRET`** (`docker-compose.yml:51–52`)
  — the key to everything sealed at rest (every AI Account credential) and
  the secret that signs sessions.
- **Postgres reach** and the AI Gateway, which pools every AI Account.

This is why both findings are **critical** by the PRD's definition ("the
host can be taken or used without the Owner's authority"). The exec is the
whole of the breach; everything after it is already in reach.

### What each fix must make true (for the remediation issues; not how)

- **S1-1:** No git command AI Office runs in a repository an Agent has
  written may execute any program that repository's config, hooks or
  attributes name — including `core.fsmonitor`, any `.git/hooks/*`,
  `filter.*.clean/smudge`, `diff.external`, `core.sshCommand`,
  `uploadpack.packObjectsHook`, and anything an `include.path`/`includeIf`
  could pull in. The guarantee must hold for `git status`, `git add` and
  `git commit`, and for every future call site, not only the three vectors
  proven here.
- **S1-2:** Sandcastle's worktree management and merge-back must not run any
  hook or config-named program from the Agent-written repository either, or
  AI Office must not run the Agent's worktree with Sandcastle's host-side
  git in the Docker-socket-holding container.

## Could not be exercised here, and what would

- **End-to-end detonation in the real app container** (planted hook →
  Docker socket → root on host) needs Docker, which is absent in this
  sandbox. The probe proves the exec deterministically at the git layer;
  the socket-to-root step is established from `docker-compose.yml` and is
  not in doubt (write access to the socket is root-equivalent by design).
  On the live stack, position 3's harness (PRD "How the red team is wired")
  would plant `.git/hooks/post-commit` in a worktree, trigger a Fresh Start,
  and have the hook `docker run -v /:/host` to confirm.
- **Driving Sandcastle's full worktree manager** (its Effect runtime and a
  configured sandbox run) was not reproduced here; S1-2 pins Sandcastle's
  `execGit` environment and subcommands exactly as read from the installed
  package. A live run with two sessions on one issue exercises the reuse +
  `git merge` path directly.
