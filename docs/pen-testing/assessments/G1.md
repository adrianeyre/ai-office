## Verdict in one line

**H11 is CONFIRMED, and is worse than its opening `low`; H16 is CONFIRMED;
H19 HOLDS.** The issue a call is billed to is the caller's word, so a
sandbox slips its issue's Token Cap by naming none, escapes its own cap by
naming an issue with a higher one, and pauses another Agent by billing its
issue (G1-1, high). Every cap is checked before a call and counted after
it, so calls made at once all pass it (G1-2); Owner tools and the Terminal
have no cap at all (G1-3); an Agent's key keeps calling models after its
Agent is paused and its Floor archived (G1-4); a subscription serves
whoever sends its agent tool's User-Agent (G1-5). On the way out, the AI
Provider's error text reaches the Gateway Key holder unredacted, so an
upstream that echoes the AI Account's credential hands it to a sandbox
(G1-6), and an upstream redirect is followed with the account's
`x-api-key` and the prompt (G1-7). An Office served beyond localhost loads
with `.env.example`'s public secrets (G1-8), and ENCRYPTION_KEY cannot be
rotated (G1-9). What holds: a key names one Agent and its Floor and opens
nothing but models; session pinning and forced accounts are confined to
the caller's own key; AI Office's headers and the caller's credentials
never go upstream; credentials are sealed with AES-256-GCM bound to their
field and row; redaction holds for logs, the Activity Feed, Notices,
request history and Connections; and on the host's loopback nothing but
`/health` answers without a Gateway Key.

## Verdict on every "What to probe" bullet

### Gateway Keys: scope, revocation, another sandbox's issue, session pinning

- **Scope (per Agent? per Floor?): per Agent — HOLDS.** Each Agent has its
  own key (`keepAgentKeys`, one per `agent.created`), and `authenticate`
  names that Agent and its Floor and nothing a request can override: a
  call naming another Agent or Floor is still attributed to the key's. An
  Agent's key is `access: "proxy"`; it cannot sign in to the web app
  (`uiKey` refuses it) and cannot be given UI access
  (`agentKeyNoUi`). It is kept as a SHA-256, and sealed (for its sandboxes)
  under `gateway_key:<id>`, so it opens in no other row. Pinned in
  `agent-keys.pen-test.test.ts`, "a Gateway Key's scope", and in
  `gateway.pen-test.test.ts`, "the Agent and Floor come from the key
  alone". (An Owner tool's key *with UI access* is a full Owner
  credential; that is A1-1 and A1-3's.)
- **Revocation: HOLDS where it exists; FINDING (G1-4) on its reach.**
  Rotation (`issueAgentKey`) and removing the Agent (`agent.removed`)
  revoke the key at once: the Gateway answers 401 to it from the next call
  (pinned). An Agent's key cannot be revoked alone, only rotated, by design.
  But nothing else ends it: the key a sandbox was given keeps calling
  models after the sandbox has gone, after the Owner pauses the Agent
  (FR-11) and after the Owner archives its Floor, "which stops all work"
  (FR-9). A key taken from one task (P2-1, S2-1) works until the Owner
  thinks to rotate it. Pinned in `agent-keys.pen-test.test.ts`, "G1-4".
- **What one sandbox's key can do with another's issue: FINDING (G1-1),
  H11.** The issue and pull request are `x-ai-office-issue` and
  `x-ai-office-pull-request`, which the sandbox is told in its environment
  (`ANTHROPIC_CUSTOM_HEADERS`, `AI_OFFICE_ISSUE`) and which code in it can
  change or drop. The Gateway takes them as sent (`workOf`) and the caps
  read them (`capCheck`, `observe`). So the coder's sandbox can bill QA's
  issue, use up its cap, and QA is paused before it has used a token.
  Confined to the key's own Floor: the Floor comes from the key, so naming
  `#9` bills web-shop's `#9`, never blog's (pinned).
- **Session pinning: HOLDS.** The session a request names is keyed under
  the caller's key (`<keyId>:<session>`), so a sandbox naming another
  key's session — even with that key's id in the name — gets a session of
  its own. Forcing an AI Account (`x-ai-office-account`) is honoured only
  for an Owner tool; an Agent's is ignored. Within its own key a sandbox
  may name any session; that moves its own stickiness and its own Context
  Usage (FR-84) only. Pinned in `gateway.pen-test.test.ts`, "session
  pinning and forced accounts".

### Attribution headers: bill another issue, slip a per-issue cap, pin a session

**FINDING (G1-1), H11.** Every part of H11 is confirmed except session
pinning (above). In `enforcement.pen-test.test.ts`, with each call 425
tokens and caps of 1,000:

- **Slip the issue's cap:** #4's cap holds while calls name #4 (paused at
  1,275, refused). The same work naming no issue spends 2,125 tokens,
  none of them counted against #4, and is never paused.
- **Escape the Agent's own cap:** the most specific cap applies (FR-32)
  and the issue is the caller's word, so the coder (own cap 1,000) names
  #7, which the Owner gave 1,000,000 for QA's big job, and spends 2,125
  tokens of its own without being paused. Any issue on the Floor with a
  higher cap — including one the Owner raised from a "Raise cap" Notice —
  lifts every Agent on the Floor to it.
- **Bill another issue:** the coder's calls naming #9 use up #9's cap; QA,
  working #9, is refused and paused on its first call.

This also falsifies the analytics' issue breakdown (FR-43) and the
request history's "for #4, PR #7".

### Token Caps: every cap, and whether it can be evaded

| Cap | Verdict |
|---|---|
| Office (each Agent's default) | Holds when nothing below it is evaded (§5 scenario 5, `enforcement.test.ts`); evaded through G1-1 and G1-2 |
| Floor (a default for its Agents) | As the office's. Note: it caps *each* Agent, not the Floor: every Contractor a chat Batch adds (P2-3) gets it afresh, so a Floor's spend grows with its team |
| Agent | **FINDING (G1-1)** escaped by naming an issue with a higher cap; **FINDING (G1-2)** passed by calls made at once |
| Issue | **FINDING (G1-1)** slipped by naming none; used up by another Agent |
| Communications Agent | Holds: the office's caps against its own use (`communicationsCapRefusal`, existing tests) |
| Keep-alive pings | Holds: asked before each (`keep-alive.ts`), counted to their Agent |
| The Manager (its chat, its judgements) | Holds: an Agent's key, capped as any Agent's (pinned, "the Manager chat's Gateway path") |
| Owner tools, the Terminal | **FINDING (G1-3)**: none. FR-33 "Owner tools (FR-46) can have caps too"; the guide says "Owner tools have no caps yet" |

- **G1-2 (concurrent calls):** the Gateway asks `check` before a call and
  `observe` after it is recorded, with no reservation for calls in
  flight. Ten calls made at once against a 1,000-token cap were all served
  (4,250 tokens, four times the cap); the Agent was paused only afterwards.
  How far past the cap is the sandbox's choice: as many calls as it opens
  at once, each up to its `max_tokens`. Pinned in
  `enforcement.pen-test.test.ts`, "G1-2".
- **G1-3 (Owner tools):** with the office's caps at 1,000 a day and 2,000 a
  month, an Owner tool's key and the Terminal's each spent 2,550 tokens,
  never refused (`capCheck` is asked only for `caller.kind === "agent"`).
  A stolen Owner-tool key (position 4) spends the Owner's AI Accounts
  without limit until it is revoked. Pinned, "G1-3".

### AI Account credentials: at rest, in transit, in request history, in error messages

- **At rest: HOLDS (confirm, don't re-test: confirmed).** AES-256-GCM, a
  random 12-byte IV, a 16-byte tag, and the format, key version and a
  context as associated data. Every call site passes a context: per row
  for multi-row secrets (`ai_account.credential:<id>`, its refresh token,
  `gateway_key:<id>`, a Connection's credentials, a request body's
  `gateway_request.body:<id>:<part>`) and per field for single ones (the
  webhook secret, the TOTP secret, the proxy password). A sealed value
  opened in another row or field, relabelled to another key version, or
  with one bit changed, is refused. Owner tools' keys are never kept, only
  hashed. Pinned in `config.pen-test.test.ts`, "secrets at rest and in
  logs", and `agent-keys.pen-test.test.ts`.
- **In transit to the upstream: HOLDS for where it is sent; FINDING
  (G1-7) on redirects.** The account's credential replaces the caller's
  (`authorization`, `x-api-key`, `proxy-authorization` and `cookie` are
  dropped); AI Office's headers are never forwarded; the query string the
  caller adds cannot move the request off the account's host; an AI
  Account's endpoint cannot be changed after it is added (the update
  schema has no endpoint), so a stolen session cannot re-point a stored
  credential. But Node's `fetch` follows a redirect, and on a
  cross-origin one strips only `authorization`: an AI Provider endpoint
  answering 307 to another origin gets that origin the account's
  `x-api-key` (an Anthropic API key's, or an Anthropic-compatible
  endpoint's in `both` mode) and the whole prompt. Pinned in
  `gateway.pen-test.test.ts`, "G1-7". Who answers with the redirect is
  outside positions 1–5 (a compromised or spoofed endpoint, or an
  on-path attacker to a plain-http custom endpoint, which is #197's), so
  it is rated low.
- **In request history: HOLDS.** Credential headers are recorded as
  `[REDACTED]` (`shownHeaders`), and both header sets pass the redactor;
  bodies are kept only while the Owner has body storage on, sealed per
  request and part, and redacted as they are read back. Fixtures record
  the forwarded headers, never the account's. Pinned in
  `gateway.pen-test.test.ts` and `redaction.pen-test.test.ts`.
- **In error messages: FINDING (G1-6).** The Gateway's own errors name no
  credential, and its logs name the account, never its key. But the AI
  Provider's error is sent to the caller as it came: passed through
  whole, or its `message` translated (`upstreamError`). An upstream that
  names the credential it was given (an OpenAI-compatible endpoint, a
  proxy in front of one, or a provider that echoes a key not allowed a
  Model) hands the AI Account's credential to the sandbox — the one place
  ADR 0001 says it never reaches. AI Office itself knows the risk: the
  usage refresh never keeps such a body ("it is the AI Provider's, and
  may echo the token", `accounts.ts`). Pinned in
  `gateway.pen-test.test.ts`, "G1-6", passed through and translated.
- **Related, G1-5 (FR-35):** a Claude subscription serves only Claude Code
  and a ChatGPT one only Codex, "as that provider's terms require". The
  Gateway decides which agent tool sent a request from its User-Agent
  alone (`agentToolOf`), which the caller sets. A Grok Agent's sandbox, or
  any code holding any key, sending `claude-cli/…` is told to the accounts
  as Claude Code and served by the Owner's subscription with raw API calls
  — a use the provider's terms forbid, which puts the AI Account itself at
  risk. Pinned in `gateway.pen-test.test.ts`, "G1-5". Related, and not a
  finding: a key is not bound to its Agent's AI Provider or Model; any
  key may ask for any Model (FR-46 scopes keys to "calling models" only).

### Redaction: logs, events, Notices, Activity Feed, Connections, request history

**HOLDS** (`redaction.pen-test.test.ts`). One redactor, as the server
wires it: every AI Account credential is registered as the process opens
it, every Gateway Key as it is made or opened, and the configured secrets
at start; anything shaped like a credential (`aio_gk_…`, `sk-ant-…`,
bearer values, PEM keys, credential-named JSON fields…) is removed by
pattern. An Anthropic-compatible endpoint's key of no known shape, and a
Gateway Key, written into a log line (message, nested object and an
error), an event, a Notice, a request body and a Notice sent to a webhook
Connection, appear in none of them. Connections redact again on their own
(`communications.ts`) and never repeat their own credentials in a failure
(`errorText`). The Gateway's live log stream is fed by the same logger.

Note (not a finding): a credential of no known shape is redacted only once
this process has opened it. After a restart, until its account first
serves (or `holdsCredential` is asked), its value is not registered. AI
Office never writes it anywhere in that window, so nothing is exposed; it
is recorded so a later change that writes a credential before opening it
does not assume otherwise.

### Weak and plaintext secrets; key rotation

- **`.env.example` values boot with a warning: FINDING (G1-8), H16.** An
  Office configured as served beyond localhost (`HOST=0.0.0.0`, an https
  `PUBLIC_URL`, `TRUST_PROXY=1`) loads with `.env.example`'s
  `SESSION_SECRET` and `ENCRYPTION_KEY`; `startServer` only warns. With the
  public ENCRYPTION_KEY, a database dump or backup opens every AI Account
  credential, Agent Gateway Key, Connection credential and TOTP secret
  sealed in it. `POSTGRES_PASSWORD=devpassword`, which compose builds
  DATABASE_URL from, is not even named by the warning. Pinned in
  `config.pen-test.test.ts`, "G1-8".
- **Plaintext secrets: CONFIRMED, as documented.** `GITHUB_APP_PRIVATE_KEY`,
  `SESSION_SECRET`, `ENCRYPTION_KEY` and the database password are in
  `.env` and the app container's environment. Each is registered with the
  logger (`secretValues`, pinned). Whatever reads the app's environment
  (H1, fixed in S1) gets them all; that is the deployment's decision, and
  the control is that nothing an Agent runs reaches the app process (S1,
  S2). Not filed again here.
- **Key rotation: FINDING (G1-9), H16.** The sealed format carries a key
  version and `createEncryptor` takes a keyring (pinned: a version-1
  value opens beside version 2), but the server is configured with one
  key and builds `encryptorFromKey` (version 1 only); `.env.example` warns
  "Changing ENCRYPTION_KEY later makes saved AI Account credentials
  unreadable". So a leaked key (G1-8 is one way) cannot be replaced
  without losing every sealed credential.

### Added after #204: the Gateway on the host's loopback (H19)

**HOLDS** (`gateway.pen-test.test.ts`, "H19").

- **Every route on 3047 without a Gateway Key:** each model route (Messages,
  count_tokens, Chat Completions, Responses, compact, systemone) answers
  401, as it does to a key not in use and to a key sent in a cookie;
  `/v1/models`, `/models`, `/usage`, `/metrics`, `/v1/usage`, `/` and the
  web app's API paths are 404 (the Gateway has no other routes). Nothing
  reaches the AI Provider. Only `/health` answers, as FR-47 intends, with
  `{"status":"ok","account":"available"|"none"}`.
- **CORS and `Host` (DNS rebinding):** no route grants any origin: a
  preflight is 404 with no `Access-Control-Allow-Origin`, and a "simple"
  cross-origin POST a browser would send unasked is 401. The `Host` header
  is not checked, so a rebinding page (`attacker.example` resolving to
  127.0.0.1) is same-origin to 3047 and can read `/health`: whether an
  AI Account is available, and nothing else. A browser sends no Gateway
  Key on its own, so it has no way past the 401.
- **Another local user or process:** reaches 3047 and gets what a browser
  does, unless it holds a key. Owner tools' keys are shown once and kept
  only as hashes; Agents' keys live sealed in Postgres and in the sandbox
  containers' environments (readable to the Docker group, which is root
  on the host anyway); the red team's credentials package is `0600`.

### Added after #204: AI Account usage windows and charts

**HOLDS** (`analytics/routes.pen-test.test.ts`, and `subscriptions.test.ts`
existing). Usage windows are read from numbers in an answer's
`anthropic-ratelimit-unified-*` and `x-codex-*` headers
(`usage-windows.ts`), and, for a subscription, from its usage endpoint (a
URL fixed in code) with its own access token as a bearer token — never an
API key's, and the body is never kept on failure. The web app's analytics
(series, breakdown, insights, usage windows), the AI Accounts list and the
request history, read through the real app with an account and a recorded
reading present, carry no credential: AI Accounts are sent as
`AiAccountInfo`, "everything but its credential".

### Added after #204: the Manager chat's Gateway path

**HOLDS as wired; G1-1 to G1-5 apply to it.**
`chat-gateway.pen-test.test.ts` drives the real `dockerSessionTool` for
Claude Code and Codex: each turn asks for the Manager's own key (by the
Manager's id) and is given only the Gateway's URL and that key, with its
conversation as the session and no issue; no GitHub token, no AI Account
credential, no other key. At the Gateway the Manager is an Agent like any
other: its calls are attributed to it and its Floor, and held to its own,
its Floor's or the office's cap (pinned in `enforcement.pen-test.test.ts`).
Reviewers and the Manager's one-shot calls (`gatewayModelClient`, and
`throughAgentTool` when only a subscription can serve) use the same
per-Agent key. P2-1 showed the session can read its key and send it out;
with it, an attacker can do at the Gateway what G1-1 to G1-5 say any
Agent's key can, until the Manager's key is rotated (G1-4).

### Why these severities

- **G1-1 high**, raised from H11's opening `low`: a Token Cap boundary is
  crossed three ways, and one Agent's sandbox reaches another Agent (it
  pauses it). The issue cap's only control is the caller's honesty.
- **G1-2 medium:** the cap is weaker than Goal 3 ("an Agent can never …
  spend without bound") and FR-33 claim; a burst is bounded by what the
  sandbox sends at once and upstream rate limits, and the Agent is paused
  after it.
- **G1-3 medium:** a control FR-33 names is absent; the guide records it as
  "not yet", with no control in its place.
- **G1-4 medium:** the key's boundary is undefended in depth: the Owner's
  own stop controls (pause, archive) do not reach it. Rotation does, which
  keeps it from high.
- **G1-5 medium:** FR-35's control is weaker than documented; the harm is
  to the Owner's AI Account standing with its provider, not a crossing of
  a key or cap boundary.
- **G1-6 medium:** ADR 0001's "never a real AI Account credential" in a
  sandbox is undefended in depth: it rests on each upstream's error
  wording. Were an upstream to echo a working key, this would be critical
  by the PRD's definition; re-rate if one is found that does.
- **G1-7 low:** needs control of an upstream's answer, which no position
  1–5 gives; defence in depth on the way out.
- **G1-8 low**, as H16 opened it: it needs a second compromise (the
  database or a backup) to use the public key; the warning is the only
  control.
- **G1-9 low:** hygiene; a documented "later piece of work" (`crypto.ts`)
  with no recorded control.

## Could not be exercised here, and what would

- **A live sandbox spoofing its headers.** Here a call with the headers
  and User-Agent a sandbox can send stood for it. On the pen-test stack,
  position 3's harness would run `curl` from inside a coder's sandbox
  against `app:3047` with its own `ANTHROPIC_AUTH_TOKEN`, naming another
  issue, no issue, and `user-agent: claude-cli/…`, and read the request
  history and the caps on the Floor admin.
- **Real upstreams.** Which real AI Providers echo a key in an error
  (G1-6), or redirect (G1-7), was not observed: there is no network to them
  here, and the pen-test stack's stub upstream answers as the probe tells
  it. The stub upstream would be set to echo and to redirect.
- **The published port and a real browser.** `127.0.0.1:3047` as Docker
  publishes it, a real DNS-rebinding page, and another local user on an
  EC2 host need the stack on a host. The Gateway's own answers (what any of
  them can reach) are pinned here.
- **Postgres stores.** The probes use the in-memory stores the server's
  own tests pair with Postgres; the authentication, caps and sealing code
  above them is the same.
