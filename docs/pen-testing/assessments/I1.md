## Verdict in one line

**H13 is CONFIRMED, H15 is CONFIRMED, H17 is CONFIRMED, and H20 still
holds where the register left it, with two write-token observations.** No
Owner-triggered fetch blocks a loopback, link-local or private address:
the custom AI endpoint is the sharpest — the Gateway fetches it and hands
the body back to the Gateway Key holder, so the EC2 metadata service's
role credentials can be read into an untrusted sandbox (I1-1). The webhook
Connection and Skill/Template import reach internal hosts too, but one is
blind and the other git-only (I1-2, I1-3). Images are pinned by tag, not
digest, and the sandbox images install Claude Code by `curl | bash`
(I1-4, I1-5). The release workflow runs its whole dependency tree under a
write token (I1-6), and the Pages build job carries deploy scopes it never
uses (I1-7). The documents understate the surface in three places (I1-8,
I1-9, I1-10), and the version check accepts and shows whatever answer it
is handed (I1-11).

What holds: the deployment binds every port but Caddy's to the host's
loopback; CI is SHA-pinned, `contents: read`, `persist-credentials:
false`, with no `pull_request_target` or `workflow_run`; `pnpm audit
--prod` is clean; and the website serves nothing the app trusts at run
time.

## Verdict on every "What to probe" bullet

### The EC2 + Caddy deployment: ports, TLS, the restriction to the Owner, IMDS, backups

**HOLDS, with the IMDS gap owned by S2.**

- **Ports: HOLDS** (`supply-chain.pen-test.test.ts`, bullet 1). The
  compose file publishes the app on `127.0.0.1` by default
  (`${AI_OFFICE_BIND_ADDRESS:-127.0.0.1}`), and the OAuth callback (1455)
  and the Gateway (3047) on `127.0.0.1` only. Postgres publishes no port.
  Under the `tls` profile only Caddy's 80, 443 and 443/udp are published.
  `deploying-to-ec2.md` says plainly: "never open ports 3045, 3047 or
  3048", and restricts 443 to the Owner's IP or a tailnet, leaving 80 open
  only for the ACME challenge.
- **TLS: HOLDS (read).** Caddy obtains and renews a certificate for
  `AI_OFFICE_DOMAIN`, redirects HTTP to HTTPS and proxies everything,
  streams included; the Gateway is not proxied (ADR 0001). Caddy sets no
  security headers — that is **A1-6** (#192), not re-filed here.
- **The restriction to the Owner: HOLDS (read).** A security group limited
  to the Owner's IP, or a Tailscale tailnet with no inbound rules. The
  setup screen before a password exists is **H4/A1** (#192).
- **IMDS: FINDING, owned by S2.** The documented set-up (Ubuntu 24.04,
  IMDSv2 only, no hop limit, an IAM role for S3 backups) lets a container
  read the instance role's credentials — **S2-2** (#193). Not re-filed.
  I1-1 is what makes that reachable from a *fetch* rather than from inside
  a sandbox: the metadata service answers the Gateway's own request.
- **Backups: HOLDS (read).** `deploying-to-ec2.md` §9 keeps the Postgres
  volume and `.env` (above all `ENCRYPTION_KEY`), a nightly `pg_dump` with
  a 14-day prune, optional S3 copy through the instance role, and EBS
  snapshots; the root volume is encrypted. The dumps are not encrypted at
  rest on the instance, but they sit on an encrypted volume and hold only
  what the database holds (AI Account credentials stay sealed with
  `ENCRYPTION_KEY`, which the dump does not carry). No finding.

### Owner-triggered fetches: can any reach Postgres, the metadata service or `app:3047` and return what it read?

**FINDING on all three paths (H13 CONFIRMED). None blocks an internal
address.** They differ in what comes back.

- **Custom AI endpoints: FINDING (I1-1).** An endpoint account's
  `endpointUrl` (FR-35) is the AI Account's `baseUrl`, which the Gateway
  fetches on every model call and whose body it returns to the caller.
  Nothing checks the host: `endpointUrl` accepts `http://127.0.0.1`,
  `http://169.254.169.254/…`, `http://app:3047`, `http://postgres:3048`,
  `https://[::1]` and plain http (pinned). The Gateway has no
  loopback/link-local/private guard either; the probe stands a fake
  metadata service on loopback, makes a call with a sandbox's Gateway Key,
  and reads the role-credential-shaped body back. So a stolen session
  (position 4) that adds an endpoint account turns the Gateway into a
  confused deputy that reads an internal service and returns it to a
  sandbox the same attacker holds (position 3) — the one place ADR 0001
  says internal/credential data never reaches. G1 (#195) deferred this
  here; **G1-7** is the complementary redirect-off-origin.
- **The generic webhook Connection: FINDING (I1-2).** `webhookCredentials`
  accepts any http or https host, internal ones included (pinned). The
  transport POSTs AI Office's (redacted) message there; it does **not**
  return the body (`response.body?.cancel()`, FR-95). So it is a blind
  SSRF with a status/timing oracle: a 502 is reflected to the Owner as
  "The webhook answered 502.", a closed port as "could not be reached"
  (pinned). It cannot read Postgres or the metadata service's content,
  only confirm what is listening.
- **Skill and Floor Template import: FINDING (I1-3).**
  `skillRepositoryUrlSchema` (shared by both) is https-only and bars
  credentials, a query and a fragment, but not the host: internal https
  hosts are accepted (pinned). `withShallowClone` has no address block.
  The clone's outcome is an oracle — a reachable host clones past the
  connection and fails differently from a refused port, and the Owner is
  shown each (pinned). Content comes back only as a git clone of an actual
  git server would give it (not Postgres, not the metadata service), so
  this is reconnaissance, not content theft. A hostile imported Template
  that names another repository (position 2) carries the URL as well as
  the Owner (position 4).
- **The outbound proxy: HOLDS as its own path (read); folded into the
  family.** `outboundProxyUrlSchema` accepts any http/https host and
  bypasses loopback, so the Owner can point the Gateway's upstream traffic
  at an internal host. But it is a *forward proxy*: it cannot return an
  internal service's content, only act as a blind connection oracle (the
  same shape as I1-2, visible to the Owner through Gateway errors). Not
  separately filed. Only the Owner sets it (position 4).

### Images: pinned by tag or digest; `curl | bash` in sandbox images; what a re-pointed tag would run

**FINDING (H15 CONFIRMED).**

- **Tag, not digest: FINDING (I1-4).** `postgres:18-alpine` and
  `caddy:2-alpine` in compose, and `node:${NODE_VERSION}-slim` /
  `-bookworm` in every Dockerfile, are tags; none carries an `@sha256:`
  digest (pinned). A re-pointed tag — a registry or namespace compromise,
  or the tag moving within its series — serves new code into the app and
  every sandbox at the next pull or build. The ARG-based `node:` reference
  cannot carry a digest at all without a change of form.
- **`curl | bash`: FINDING (I1-5).** `docker/sandbox-claude/Dockerfile`
  installs Claude Code with `curl -fsSL https://claude.ai/install.sh |
  bash` (pinned). All three sandbox images add the GitHub CLI by fetching
  a key and apt source, and install pnpm, Codex (`@openai/codex@latest`)
  and opencode (`opencode-ai@latest`) from their registries at a moving
  version (pinned). A compromised installer, key, apt source or package
  runs at build time, as the `agent` user, in the image every Agent works
  in. Nothing pins what any of them resolves to.
- **What a re-pointed tag would run:** not exercised (no Docker). On the
  stack, `docker compose pull` and `pnpm sandbox:build` would fetch
  whatever the tag then points at; digests would refuse a changed image.

### CI: actions SHA-pinned, `contents: read`, `persist-credentials: false`, no `pull_request_target` / `workflow_run`; and H20

**HOLDS for the "Confirm, don't re-test" line; FINDING on H20's new
workflows.**

- **SHA-pinned: HOLDS.** Every `uses:` in every workflow is
  `owner/repo@<40-hex>` (pinned).
- **`persist-credentials: false`: HOLDS.** Every `actions/checkout` sets
  it, `release.yml` included (pinned).
- **No `pull_request_target` / `workflow_run`: HOLDS.** No workflow uses
  either (pinned). `ci.yml` triggers on `push` to `main` and
  `pull_request`; `release.yml` on `push` to `main`; `pages.yml` on
  `push` to `main` (paths) and `workflow_dispatch`.
- **`ci.yml` is `contents: read`: HOLDS** (pinned).
- **`release.yml`: FINDING (I1-6), H20 confirmed.** Top-level permissions
  are `contents: read`, but the `release` job raises them to `contents`,
  `issues` and `pull-requests: write`, then runs `pnpm install
  --frozen-lockfile` (which runs allowed install scripts) and `pnpm exec
  semantic-release` (a large dependency tree), all under that token, with
  `GITHUB_TOKEN` in the step's environment (pinned). A compromised
  dependency anywhere in that tree runs with write to the repository's
  contents, issues and pull requests on every merge to `main`.
- **`pages.yml`: FINDING (I1-7), H20 confirmed.** `pages: write` and
  `id-token: write` are top-level, so the `build` job carries them even
  though it only runs first-party `node site/build.ts` (no install, no
  dependencies) and uploads an artifact; only `deploy` needs them (pinned).
  Least-privilege in depth; there is no dependency code in the build job
  today, so the exposure is latent.

### Documentation drift: FR-1/FR-2; `.env.example` on Gateway authentication; the compose comment on sandbox reach and the Gateway port; `docs/guide/ai-gateway.md`

**FINDING (H17 CONFIRMED) in three places; the guide and the Gateway-port
comment hold.**

- **FR-1/FR-2: FINDING (I1-8).** FR-1 and FR-2 speak of "the password" and
  name no further Owner password and no API-key sign-in, while the code
  has both (`POST /api/owner-passwords`, `POST /api/login/api-key`), as
  A1 (#192) and H5 exercised (pinned). An Owner reading the requirements
  under-counts the ways in.
- **`.env.example` on Gateway authentication: FINDING (I1-9).** It says
  the Gateway "has no authentication of its own yet (Gateway Keys come
  later)", while the code requires a Gateway Key on every request and the
  guide says so: "Every request to the Gateway presents a Gateway Key"
  (pinned). The comment reads as if the Gateway were open.
- **The compose comment on sandbox reach: FINDING (I1-10).** The
  `networks:` comment says sandboxes reach "the AI Gateway as app:3047 and
  nothing else of the stack", which S2-3 (#193) disproved: the app also
  answers 3045 and 1455 on that network (pinned). An Owner trusts a
  boundary that is not there.
- **The compose comment on the Gateway port: HOLDS (read).** The `ports:`
  comment says the Gateway is published on `127.0.0.1:3047` and "is never
  reachable from the network"; that is true of the host publish (H19/G1
  confirmed only `/health` answers without a key). It does not claim
  anything about the sandboxes' network, so it is not the I1-10 drift.
- **`docs/guide/ai-gateway.md`: HOLDS (read).** It matches the code:
  loopback by default, a Gateway Key on every request, a 503 with no
  account. It is `.env.example` (I1-9) that is the outlier.

### The version check: the URL fetched, what a hostile or spoofed answer can do, caching of failures

**HOLDS on the shape; FINDING (I1-11) on input validation.**

- **The URL: HOLDS.** The server asks one fixed URL,
  `https://raw.githubusercontent.com/adrianeyre/ai-office/main/package.json`
  (pinned), so there is no SSRF and the browser loads nothing from other
  sites. The route is owner-access (401 without a session, pinned).
- **A hostile or spoofed answer: FINDING (I1-11).** `latestVersionSchema`
  is `version: string().min(1)` — no shape, length or character class — so
  any string is accepted and returned to the web app whole, a 5,000-char
  one included (pinned). An on-path attacker between the server and
  raw.githubusercontent.com (outside positions 1–5, as G1-7) could show
  the Owner an attacker-chosen "version" and a standing out-of-date nag.
  The blast radius is bounded: the web app renders it as React text
  (escaped) and builds the GitHub link with `encodeURIComponent`
  (`releasePageOf`), so no `javascript:` scheme and no markup injection
  (pinned). Rated low.
- **Caching of failures: HOLDS (read).** A success is kept 10 minutes, a
  failure 1 minute, with one question in flight at a time; a failure
  answers 502 with `cache-control: no-store`. No unbounded retry, no
  stampede.

### The website (`site/`, GitHub Pages): anything served from it that the app trusts

**HOLDS (read).** The site is static marketing assembled by
`site/build.ts` and published by `pages.yml`. The running app trusts
nothing served from it: the version check reads raw.githubusercontent.com
(above), and the footer's version is `__APP_VERSION__`, compiled in from
`package.json` at build time, not fetched from the site. The site as a
service is out of scope. No finding.

### Why these severities

- **I1-1, medium (re-rated up from H13's low):** the premise the register
  rated low has changed — this path *returns content*, and the content can
  be the EC2 instance role's credentials (via the metadata service, S2-2)
  handed to an untrusted sandbox, which is a boundary ADR 0001 draws and
  undefends. Not high: it needs a stolen session (position 4) to add the
  account, and the Gateway Key holder reading the answer is the same
  attacker. Re-rate at the exposure gate if the instance role is wide.
- **I1-2, I1-3, low (as H13):** blind (I1-2) or git-only with an error
  oracle (I1-3); each needs a stolen session, or a hostile Template, and
  neither returns an arbitrary internal service's body.
- **I1-4, I1-5, low (as H15):** supply-chain hygiene. Each needs a
  registry, tag, installer or package compromise to fire; nothing an
  in-scope attacker does triggers it. Digests and vendored installers are
  depth against that day.
- **I1-6, I1-7, low (as H20):** each needs a compromised dependency (I1-6)
  or a future dependency added to the Pages build job (I1-7). The register
  rated H20 low; nothing here changes the premise.
- **I1-8, I1-9, I1-10, low:** disclosure. A documented decision whose
  recorded surface is narrower than the code's; A1 (#192) and S2 (#193)
  own the live findings these describe.
- **I1-11, low:** the attacker must be on-path to GitHub (outside
  positions 1–5), and the displayed string is escaped and the link
  encoded, so the blast radius is a nag and attacker-chosen text in a
  version number.

### What each fix must make true (for the remediation issues; not how)

- **I1-1:** No Owner-triggered fetch — a custom AI endpoint above all —
  reaches a loopback, link-local, or private address, or the stack's own
  services, unless the Owner has explicitly allowed that host; and the
  Gateway never returns an internal service's body to a Gateway Key holder.
- **I1-2:** A webhook Connection cannot be aimed at a loopback,
  link-local, private or stack-internal address unless the Owner
  explicitly allows it; the same host policy as I1-1.
- **I1-3:** Skill and Floor Template import refuse an internal, loopback or
  link-local host, so a clone cannot be used to probe the stack's network.
- **I1-4:** Every image the stack runs is pinned by digest (or an
  equivalent content pin), so a re-pointed tag cannot serve new code.
- **I1-5:** The sandbox images install their agent tools and CLIs from
  pinned, verified artifacts, never by piping a fetched script into a
  shell at a moving version.
- **I1-6:** No job that runs third-party dependency code holds a write
  token; the release that needs one runs that step with the narrowest
  scope and nothing untrusted alongside it.
- **I1-7:** The Pages `pages: write` and `id-token: write` scopes are
  granted only to the deploy job, not to the build job.
- **I1-8:** FR-1/FR-2 describe every way the Owner signs in: several Owner
  passwords and API-key sign-in.
- **I1-9:** `.env.example` says a Gateway Key is required, as the code
  demands and the guide says.
- **I1-10:** The compose comment says what a sandbox actually reaches on
  the sandboxes' network (the Gateway, and the app's 3045 and 1455; since
  S2-3, the Gateway through the sandbox relay alone).
- **I1-11:** The latest-version answer is validated as a version number
  before it is cached, shown or linked; anything else is treated as "could
  not find out".

No Docker, no EC2, no second host, and no network beyond the registry and
the model. On the pen-test stack:
