# Pen-testing: the pen-test stack

The target of the first adversarial round: AI Office as the red team
probes it, in a `docker compose` stack of its own. The brief is the
[pen-testing PRD](../product-requirements-document/pen-testing.md)
(Engagement shape, "Target", and Sequence step 3); this page is how the
Owner stands the stack up, what it is for, what it must never be, and how
it is torn down. Its files are in [`docker/pen-test/`](../../docker/pen-test/).

## What it is for

- **The red team's target.** Every probe in the A, S, P, G, W and I
  series runs against this stack, at one pinned commit, and nothing else.
  Destructive testing is allowed here and nowhere else, within the
  [rules of engagement](rules-of-engagement.md#targets).
- **Attacker position 2's victims.** Its target Floor works the
  throwaway target repository, seeded with hostile issues and files
  (seed data: E2, #188).
- **Attacker position 3's sandboxes.** Its sandboxes are started by its
  own app, on its own sandboxes network, with its own work directory.
- **A place where a leaked credential is worthless and detectable.** It
  holds no real AI Account credential: its AI Accounts point at a stub
  upstream with canary credentials.

## What it must never be

- **Never the Owner's real Office**, or run beside it on a shared
  database, volume, secret, GitHub App, sandboxes network or sandbox work
  directory. Stand-up refuses a secret the real stack also holds and the
  real Office's GitHub App.
- **Never a shared host.** Run it on the Owner's own machine or an
  instance of its own.
- **Never holding a real credential.** No real AI Account is ever added
  to it, and its GitHub App is installed on the throwaway target
  repository alone.
- **Never reachable by anyone but the red team.** It is published on
  loopback; [opening it](#opening-it-to-the-red-teams-host) means one
  interface and a firewall that admits the red team's address alone,
  never `0.0.0.0`.
- **Never left running after the round.** [Teardown](#tearing-it-down)
  removes its database volume and its sandbox work directory, not only
  its containers.

## What is in it

`docker/pen-test/compose.yml` is the project `ai-office-pen-test`. It
reads only `PEN_TEST_` variables, so no setting of the real stack's
(`.env`, or a variable exported in the shell) can reach it.

| Service | What it is |
| --- | --- |
| `postgres` | Postgres 18, its data in the volume `ai-office-pen-test-postgres-data`, its own password. Not published. |
| `stub-upstream` | The [stub upstream](#the-stub-upstream), on `stub-upstream:3050`, on the stack's default network only. Not published. |
| `ai-accounts` | A one-off run (the `setup` profile) that applies the database schema and adds the stack's AI Accounts, each pointing at the stub upstream. |
| `app` | AI Office at the commit checked out, built as `ai-office:pen-test` (never the Owner's `ai-office:local`), published on `127.0.0.1:3145`. Its AI Gateway is `app:3047`, which sandboxes reach as `sandbox-relay:3047`. |
| `sandbox-relay` | As in the real stack ([Sandboxes](../guide/issue-pipeline.md#sandboxes)): the one thing on `ai-office-pen-test-sandboxes`, which has no route out, besides the sandboxes. It forwards `sandbox-relay:3047` to the AI Gateway and relays HTTPS to the hosts `PEN_TEST_SANDBOX_EGRESS_HOSTS` names (none by default). Its log is every connection a sandbox asked for. Not published. |
| `seed` | A one-off run (the `setup` profile, after the app) that seeds the fixtures and the hostile-content corpus, and writes the fixture ID listing (see [The seed](#the-seed), E2, #188). |
| `credentials` | A one-off run (the `setup` profile) that mints and revokes the red team's credentials and writes the [credentials package](credentials-package.md) (E4, #190). `docker/pen-test/credentials` runs it. |

The app runs as in the real stack, with the host's Docker socket, so that
what the red team finds holds for a real deployment. Its own are:

- **Secrets:** `PEN_TEST_POSTGRES_PASSWORD`, `PEN_TEST_SESSION_SECRET` and
  `PEN_TEST_ENCRYPTION_KEY`, generated by stand-up, never the
  `.env.example` values.
- **GitHub App:** `PEN_TEST_GITHUB_APP_ID` and
  `PEN_TEST_GITHUB_APP_PRIVATE_KEY`, an App made for the round. The seed
  adds it to the stack's database, as the Owner adds one in Floor
  Settings (ADR 0011), and the app takes it up within a minute.
- **Sandbox work directory:** `PEN_TEST_SANDBOX_WORK_DIR`, by default
  `~/.local/state/ai-office-pen-test/sandboxes` (under `$XDG_STATE_HOME`
  when set), at the same path in the app as on the host, because the
  host's Docker bind-mounts the clones into the sandboxes. It is never
  inside this repository, whose tests would find the clones' files.
- **Sandboxes network:** `ai-office-pen-test-sandboxes`, which Postgres
  and the stub upstream are not on.
- **Credentials directory:** `PEN_TEST_CREDENTIALS_DIR`, by default
  `~/.local/state/ai-office-pen-test/credentials`, where the
  [credentials package](credentials-package.md) is written (E4). Only the
  `credentials` service mounts it, never the app, so no sandbox reaches it;
  it is never inside the sandbox work directory or this repository.

Two things differ from the real stack, deliberately:

- **No Caddy.** The `tls` profile is the real stack's. To probe the app
  behind a proxy as the deployment documents configure it, set
  `PEN_TEST_TRUST_PROXY` and `PEN_TEST_PROXY_SECRET` (the app refuses one
  without the other). A request is believed about the client's address
  only when it carries the secret in `X-AI-Office-Proxy`.
- **Port 1455 is not published.** The pen-test stack has no subscription
  to sign in to, and `127.0.0.1:1455` belongs to the real stack. The
  sign-in callback still listens on `0.0.0.0` inside, as in the real
  stack, so H14 can be probed from a sandbox.

## Before you start

- **Docker**, and **Node 26** (the scripts need nothing installed with
  pnpm).
- **The sandbox images**, `pnpm sandbox:build`, as for the real Office:
  the stack's app starts its sandboxes from them. They hold no secret, so
  the two share them.
- **A throwaway target repository**, private, with nothing in it that
  matters. It is the repository the target Floor works and the hostile
  content is seeded into.
- **A GitHub App for the round.** Create it as for a Floor
  ([Setting up a Floor](../processes/setting-up-a-floor.md#2-create-the-github-app),
  steps 2 to 4), with a name that says it is the pen-test's, and install
  it with **Only select repositories** on the target repository alone.
  Never use the real Office's App: stand-up refuses its App ID.

## Standing it up

```bash
docker/pen-test/stand-up
```

The first run copies `docker/pen-test/.env.example` to
`docker/pen-test/.env` (git-ignored), writes new secrets and the sandbox
work directory into it, and stops, asking for the three settings only the
Owner has:

```dotenv
PEN_TEST_GITHUB_APP_ID=123456
PEN_TEST_GITHUB_APP_PRIVATE_KEY="-----BEGIN RSA PRIVATE KEY-----\n…\n-----END RSA PRIVATE KEY-----"
PEN_TEST_TARGET_REPOSITORY=your-login/pen-test-target
```

The private key goes in on one line, with `\n` for each newline. Then run `docker/pen-test/stand-up` again. It refuses to go on,
and says which setting is wrong, when:

- any of those three is empty, or the App ID is the real stack's
  `GITHUB_APP_ID`;
- a secret is also in the real stack's `.env` or the root `.env.example`
  (empty it in `docker/pen-test/.env` and stand-up generates a new one);
- the work directory is relative, inside this repository, holds the home
  directory or the repository, or is the real stack's `SANDBOX_WORK_DIR`;
- `PEN_TEST_BIND_ADDRESS` is every interface, or beyond loopback without
  `PEN_TEST_RED_TEAM_ADDRESS`.

Then it:

1. builds the app's image, `ai-office:pen-test`, from the commit checked
   out (check out the round's pinned commit first);
2. starts Postgres and the stub upstream;
3. runs `ai-accounts`: the database schema, then the stack's AI Accounts;
4. starts the app, and waits until it is healthy;
5. runs `seed` (E2, #188): the Floors, the Agents, the hostile-content
   corpus and the throwaway repository's issues and files (see
   [The seed](#the-seed));
6. prints its address, `http://127.0.0.1:3145`, and where the fixture ID
   listing was written.

**Open it at once and set the Owner password on the setup screen.** Until
a password exists, whoever reaches the setup screen first becomes the
Owner (H4); on loopback that is only this machine. Sign in, and the
Office shows the four AI Accounts under **AI Settings**, the seeded Floors
and their Agents, and the hostile content under the target Floor. Then mint
the red team's credentials and the fixture ID listing into the
[credentials package](credentials-package.md) with
`docker/pen-test/credentials mint`, and deliver it as that page says, never
in an issue, a chat or an email.

Stand-up can be run again: it keeps the secrets in `.env`, rebuilds the
image, and leaves the AI Accounts, Floors and corpus that are already
there (the seed is idempotent).

## The stub upstream

`docker/pen-test/stub-upstream.ts` answers like the AI Providers the
stack's AI Accounts are for, enough for every route the AI Gateway uses,
and logs every request it receives. It uses nothing but Node.

| AI Account | Endpoint | What the stub answers there |
| --- | --- | --- |
| Claude (pen-test stub), a Console API key | `http://stub-upstream:3050/anthropic` | `/v1/messages`, streamed or not; `/v1/messages/count_tokens`; `/v1/models` |
| Grok (pen-test stub), an API key | `…/xai` | `/v1/chat/completions` and `/v1/responses`, streamed or not; `/v1/models` |
| Gemini (pen-test stub), an API key | `…/gemini` | the same under `/v1beta/openai` |
| OpenAI-compatible (pen-test stub), an endpoint | `…/openai/v1` | the same, for Codex's Responses and any Model no other AI Provider claims |

Each answer is the same short text, "This is the pen-test stub upstream.
No AI Provider read this request.", with token usage counted from the
request's length. The model lists give each AI Provider its default
Model at start: `claude-opus-5-5`, `grok-stub`, `gemini-stub` and
`gpt-stub`. ChatGPT takes only subscriptions, so it has none until the
Owner (or the seed) chooses `gpt-stub` for it in **AI Settings**; Codex
Agents' requests then go to the OpenAI-compatible account.

**The log.** Each request is one JSON line on the stub's output: the
time, method, URL, every header exactly as received, the body (up to
1 MiB, with its full length) and the status. Only its own health check is
not logged.

```bash
docker compose --project-name ai-office-pen-test logs --no-log-prefix stub-upstream > stub-upstream.jsonl
```

Save it before teardown: teardown removes the container, and the log
with it.

**Canary credentials.** Each AI Account's credential is
`pen-test-canary-<provider>-<random>`, made when it is added and stored
only encrypted in the stack's database. The stub's log shows each one
arriving where it should (`x-api-key` or `authorization`). Anywhere else
(a sandbox's environment, a log line, a Notice, the Activity Feed, a
commit, or the body of a request the stub received) it is a leak:

```bash
grep -rn "pen-test-canary-" <wherever you look>
```

A canary credential is worthless outside the stack; it still goes in a
finding as `<redacted>`, as the [triage runbook](triage-runbook.md)
says for every credential.

## The seed

`docker/pen-test/seed-cli.ts`, run by the `seed` service at stand-up (E2,
[#188]), makes the fixtures the red team probes. It is idempotent: a
second run checks for each item before it makes it, so it changes nothing.

- **At least two Floors**, so an authorisation bug between Floors can show:
  `pen-test-target` (the throwaway repository), whose Merge Policy is
  **auto-merge**, so it merges unattended and H8 can be probed; and
  `pen-test-review`, which sends pull requests to the Owner.
- **Agents in every Stage** on each Floor: a Manager, a coder and a
  designer (work), a reviewer (review), a QA Agent and a docs Agent.
- **The AI Accounts** that point at the stub upstream only
  (`stub-accounts.ts`), as `ai-accounts` adds them; the seed ensures them
  too.
- **A hostile-content corpus for attacker position 2**
  (`docker/pen-test/corpus.ts`), as fixture data: issue bodies, repository
  files (`CLAUDE.md`, `.claude/settings.json`, `package.json` scripts, a
  shell script), a review comment, a Skill, a Floor Template with a
  `setupCommand`, and a memory proposal. Each item carries a unique canary
  string and names the hypothesis it tests (**H8**, **H9**, **H10**,
  **H13**). The canaries are harmless: each asks whoever reads it to fetch
  a URL on the stub upstream (`/canary/<canary>`, prefix
  `pen-test-canary-corpus-`), never anywhere else, so a success shows as
  one line in the stub's log. The corpus's Skill, Floor Template and memory
  proposal go in the database; its issues and files are written into the
  throwaway repository by `generate-target.ts` (as the GitHub App, labelled
  `ai-office` and `pen-test-corpus`). Running the corpus against Agents is
  #194, not E2.
- **The fixture ID listing** (`docker/pen-test/fixtures.ts`): the seeded
  Floor IDs, Agent IDs and issue numbers, written as JSON to
  `pen-test-fixtures.json` in the sandbox work directory (at the same path
  on the host), for the [credentials package](credentials-package.md)
  ([E4, #190]) to deliver. It holds no credential.

[#188]: https://github.com/adrianeyre/temp3/issues/188
[E4, #190]: https://github.com/adrianeyre/temp3/issues/190

## Opening it to the red team's host

By default only this machine reaches the stack. When the red team's
Agents probe it from another host:

1. Set `PEN_TEST_BIND_ADDRESS` to the address of **one** of this
   machine's interfaces, the one the red team's host reaches (never
   `0.0.0.0` or `::`: stand-up refuses them).
2. Set `PEN_TEST_RED_TEAM_ADDRESS` to the red team's host's address, and
   `PEN_TEST_PUBLIC_URL` to the address it reaches the stack at, if that
   is a name.
3. Run `docker/pen-test/stand-up`. It prints two firewall rules; run them
   before the window opens:

   ```bash
   sudo iptables -I DOCKER-USER -p tcp -m conntrack --ctorigdstport 3145 --ctdir ORIGINAL -j DROP
   sudo iptables -I DOCKER-USER -p tcp -m conntrack --ctorigdstport 3145 --ctdir ORIGINAL -s <red team address> -j ACCEPT
   ```

   Docker's published ports bypass `ufw` and the INPUT chain, so the rules
   go in Docker's `DOCKER-USER` chain, matched on the port as published.
   Each is inserted at the top, so the accept, run second, comes first.
   On EC2, a security group that admits only the red team's address to
   that port does the same.
4. From another machine, check the port is refused; from the red team's
   host, check it answers.

After the round, delete the rules (`sudo iptables -D DOCKER-USER …`, the
same rules with `-D` for `-I`). Opening the stack never changes the
Owner's real Office, whose address and port stay its own.

## Tearing it down

```bash
docker/pen-test/teardown
```

It says what it will remove, removes it, then says what it removed:

1. every sandbox container, with its home and `/tmp` volumes: the app
   started them through the host's Docker, so they are not the stack's
   containers. Each is on a network of its own, labelled
   `ai-office.sandbox-network=ai-office-pen-test-sandboxes`, which the
   sandbox relay joins
   ([ADR 0006](../architectural-decision-record/0006-each-sandbox-has-a-network-of-its-own.md)),
   or, if started before that, on `ai-office-pen-test-sandboxes` itself;
2. the stack's containers, with `docker compose down --volumes
   --remove-orphans`;
3. its networks, `ai-office-pen-test_default` and
   `ai-office-pen-test-sandboxes`, and each sandbox's own network;
4. its database volume, `ai-office-pen-test-postgres-data`, and any other
   volume labelled for the project that `down` left, by name; if one is
   still there afterwards, teardown fails and names it;
5. its sandbox work directory, only if stand-up made it (it holds
   `.ai-office-pen-test`) and it passes the same checks as at stand-up;
6. its credentials directory, and with it the
   [credentials package](credentials-package.md#destroyed-at-teardown), on
   the same terms;
7. its generated secrets in `docker/pen-test/.env`, so the next stand-up
   gets new ones.

It keeps the image `ai-office:pen-test` and the Owner's settings in
`docker/pen-test/.env` (the App and the target repository). To remove
the image too: `docker image rm ai-office:pen-test`. Then check nothing
is left:

```bash
docker volume ls --filter label=com.docker.compose.project=ai-office-pen-test
docker network ls --filter name=ai-office-pen-test
docker network ls --filter label=ai-office.sandbox-network=ai-office-pen-test-sandboxes
```

All three list nothing. After the round, also uninstall the pen-test GitHub
App from the target repository and delete its private key on the App's
page, or delete the App.

## The tests

`pnpm test` checks the stack without Docker (`docker/pen-test/*.test.ts`,
in the `deployment` Vitest project):

- **`compose.test.ts`**: the compose file against the Compose
  Specification, and against the real stack's: its project name, volume
  and networks; only `PEN_TEST_` variables, every secret required with no
  default, none of the root `.env.example`'s values; `.env.example` with
  every variable compose and stand-up read, each empty; only the app
  published, on `127.0.0.1` by default; the stub upstream as every AI
  Account's endpoint; the `seed` service in the setup profile, pointed at
  the stub, reading only `PEN_TEST_` variables. With Docker, `docker
  compose config` also validates it.
- **`corpus.test.ts`**: every corpus item has a unique canary and a
  hypothesis; the canaries phone home to the stub and nowhere else; the
  artefact kinds and the hypotheses H8, H9, H10 and H13 are all present.
- **`seed.test.ts`**: against memory stores and (in CI, or against a local
  Postgres) a real database, the seed makes the Floors, the Agents in every
  Stage, the unattended-merge Floor, the AI Accounts and the corpus's
  Skill, Floor Template and memory proposal, and a second run changes
  nothing.
- **`generate-target.test.ts`**: against the fake GitHub, the corpus's
  issues and files are generated, idempotently.
- **`fixtures.test.ts`**: the fixture ID listing names the Floor IDs, Agent
  IDs and issue numbers, and holds no credential.
- **`credentials.test.ts`**: the credentials package; see
  [its tests](credentials-package.md#the-tests).
- **`stub-upstream.test.ts`**: each route, streamed and not, each model
  list, the errors; the log of each request with its headers and body;
  then the stack's AI Accounts, pointing at the stub, behind the AI
  Gateway itself, serving Claude Code's, Codex's and opencode's requests
  and listing their Models.
- **`stack.test.ts`**: stand-up and teardown with the Docker CLI faked:
  what stand-up generates, refuses and runs; `credentials mint` and
  `revoke`; teardown's list, what it removes and says it removed, and that
  it deletes no directory stand-up did not make.
